# Two-host qualification and Windows-TX-to-Linux-RX throughput

## Scope

This project qualifies socket-mux across two Linux hosts, establishes a repeatable qualification path, and then measures Windows TX to Linux RX throughput while preserving byte correctness. The throughput goal is at least 80% of the 9.285 Gbit/s 10GbE payload ceiling, or at least 7.43 Gbit/s goodput sustained with zero loss. This is the P3 exit criterion for Linux-to-Linux and the P5 exit criterion for Windows-TX-to-Linux-RX. The project covers phases P0 through P5 below; it does not authorize a release, version bump, publication, or an architecture change merely because a roadmap candidate is listed.

### Starting baseline

The accepted starting implementation is the build at HEAD `3fb9443`, with behavior and architecture owned by the [specification](../docs/spec.md) and [design](../docs/design.md). It uses round-robin UDP lanes, a 24-byte header with a 16-bit session field, a preallocated RX pool bounded by `--rx-memory` (64 MiB by default), wheel/FIFO reassembly, strict in-order delivery, timeout/memory/output loss causes, one timeout T (10 s by default), `tx`, `tx-pat`, `rx`, and `check-pat`, and a default datagram size of 1452 bytes. UDP buffer readback warns when the OS caps the request; that behavior is present at `3fb9443`.

Linux x86_64 has been qualified on loopback, not on a real link: 68 tests, 64 MiB transfers at N=1 and N=16, pattern/check-pat, loss causes, session change, idle CPU 0%, and 8.5 Gbit/s loopback. This is not a two-host qualification result. macOS was tested on an earlier build; current-build retest is deferred. Linux aarch64 is deferred. The first-release qualification scope remains Linux x86_64; Windows x86_64 is next when its peer is available.

### Change boundary and environment

The target path is Host A (`192.168.7.33`) to Host B (`chuck`, `192.168.7.40`) and the reverse, followed by a headless Windows TX peer to Linux RX. Both Linux hosts are x86_64 with AMD Ryzen AI Max+ PRO 495 processors (32 threads), 10GbE, MTU 1500, and `net.core.rmem_max`/`wmem_max` of 4 MiB. Host B has no root, Rust, or socat; it has Python 3 and runs a copied static binary. Host A's root/admin capability is unknown. The Windows peer's architecture is unconfirmed; its current proposed cross target is `x86_64-pc-windows-gnu`, which requires the Rust target and zig toolchain, currently missing. If the Windows peer is ARM64, the target must instead be evaluated as `aarch64-pc-windows-gnullvm`.

Test data and logs stay on each host's local disk, never under Syncthing-mirrored `/mnt/shared`. The verification harness is `.cursor/skills/verify-socket-mux`; its artifacts default to `~/.local/state/socket-mux/artifacts`. The 4 MiB Linux socket-buffer cap, lack of root on Host B, unknown Host A admin capability, and unpaced `tx-pat` are material constraints. Jumbo MTU work waits for the Windows peer.

## Acceptance

The project is complete only when the two-host baseline is reproducible and correctness-checked, the SSH harness can repeat it with host-local artifacts, Windows TX to Linux RX is correctness-qualified, and every retained optimization has same-method evidence of improvement without new loss. The final result must report the best measured throughput, the comparison to the P1 baseline and payload ceiling, relevant loss/drop/CPU counters, and any unresolved bottleneck; no release or version change is part of acceptance.

The payload ceiling for a 10 Gbit/s link with a 1452-byte datagram (1428 payload bytes) per 1538 wire bytes is `10 × 1428 / 1538 = 9.28478543563069 Gbit/s`, or approximately 9.285 Gbit/s. Eighty percent is 7.42782834850455 Gbit/s, rounded to the owner-set threshold of at least 7.43 Gbit/s. These are arithmetic targets, not observed throughput claims.
