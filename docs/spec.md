# socket-mux Specification

## Purpose

Define the consumer-visible behavior of socket-mux: its TX and RX modes and four subcommands, its command-line interface, the input TX accepts or generates, the UDP lanes and per-datagram header it uses, the stream it reconstitutes, how it reports loss and throughput, how it ends on a signal, its configurable lane count and the platforms it supports. This specification defines the intended baseline for the socket-mux CLI, including its TX and RX modes and the `check-pat` subcommand; it does not assert that every specified behavior is implemented in any particular source revision. "Must" marks a requirement. "Gap" marks behavior this specification does not define; and a consumer relies on no particular behavior there.

| Deadline                 | The last-delivery time plus ipd. | Settled sequence number  | A sequence number at or after next whose datagram RX dropped under the buffer rule and already counted lost; next passes it without waiting and without counting it again.                                                                                                                                                                                                                                                                                                                                                                                            |
| Buffer pressure          | The state of RX from a datagram it drops under the buffer rule until an RX buffer next becomes free.                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Out-of-sequence delay    | For a datagram RX delivers that arrived after RX held a datagram with a higher sequence number: its arrival time less the arrival time of the earliest such held datagram. | Final summary            | One summary line TX or RX prints at `info` when it ends, covering the whole run.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Reporting period         | One of the consecutive periods of `--interval` seconds into which RX divides its run, the first starting at the arrival of the first valid datagram of its locked session. RX prints at most one loss warning per period, and neither TX nor RX prints any other line per period.                                                                                                                                                                                                                                                                                     |
| Loss warning             | One `warn` line in which RX reports the loss stretches of one reporting period ([Diagnostics](#diagnostics)).                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Verification loop        | TX and RX placed back to back; a pattern loop is `tx-pat` and RX placed back to back.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Total error rate         | The share of a run's datagrams that RX did not deliver: the datagrams TX sent less the datagrams RX delivered, over the datagrams TX sent, taken from the TX final summary (S-22) and the RX final summary (S-09) of the same run. It counts every lost datagram, including a lost tail that RX never declared lost.                                                                                                                                                                                                                                                  |
| Delivered fraction       | The datagrams RX delivered over the datagrams TX sent, one minus the total error rate; three nines is 99.9 % (a total error rate of 10^-3) and five nines is 99.999 % (10^-5).                                                                                                                                                                                                                                                                                                                                                                                        |

## Model

TX reads one input and splinters it into N UDP lanes, each on a different port, with a header on every datagram. The `tx` subcommand reads one TCP connection on localhost, standard input (`-`) or a file, like netcat, and RX reassembles that stream on the remote end. The `tx-pat` subcommand behaves as `tx` does, except that its input is a pattern it generates instead of an input stream, optionally limited to a byte count. TX sends each datagram as soon as its lane accepts it, without pacing. The `check-pat` subcommand reads a pattern stream from standard input and validates it; it opens no socket. RX uses the headers to sequence slices and to determine packet loss and the length of that loss, and reconstitutes the original stream. Neither network mode retransmits, so the channel is lossy. While a stream runs, RX reports loss only as grouped loss warnings; when it ends, RX prints one final summary of its throughput and loss and TX one of its sent throughput. Neither prints a line per datagram at the default log level.

```text
TCP client (127.0.0.1:31100), standard input or file -> tx -> UDP base port .. base port + N - 1 -> RX -> TCP peer (127.0.0.1:31200)
generated pattern                                      -> tx-pat -> UDP base port .. base port + N - 1 -> RX -> TCP peer -> pattern validation
```

The ports in the diagram are the defaults ([Default Ports](design.md#default-ports)).

### Command Line

#### Grammar

The binary is `socket-mux` with this grammar ([Command-Line Options](design.md#command-line-options)). socket-mux is a CLI with TX and RX subcommands and a `tx-pat` subcommand ([One Program With TX And RX Subcommands](design.md#one-program-with-tx-and-rx-subcommands)). `tx` takes an optional `INPUT` operand ([TX Input Operand](design.md#tx-input-operand)).

```text
socket-mux [GLOBAL OPTIONS] tx [GLOBAL OPTIONS | TX OPTIONS]... [INPUT]
socket-mux [GLOBAL OPTIONS] tx-pat [GLOBAL OPTIONS | TX-PAT OPTIONS]...
socket-mux [GLOBAL OPTIONS] rx [GLOBAL OPTIONS | RX OPTIONS]...
socket-mux [GLOBAL OPTIONS] check-pat [GLOBAL OPTIONS | CHECK-PAT OPTIONS]...
socket-mux --help | --version
```

Global options are accepted both before and after every subcommand, including `check-pat`. Command options appear after the subcommand ([Command-Line Options](design.md#command-line-options)). TX sends lane k to `--remote` at base port + k, and RX listens on those same ports. The operator configures both sides with the same lane count, base port and datagram size by hand; they do not negotiate.

#### Byte Counts

`--bytes`, `--rx-memory` and `--udp-buffer` each take one byte count: an unsigned decimal integer followed directly by an optional suffix, matched case-sensitively. `K` or `k` multiplies the integer by 10^3, `M` by 10^6 and `G` by 10^9 (SI prefixes); `Ki` multiplies it by 2^10, `Mi` by 2^20 and `Gi` by 2^30 (IEC prefixes). #### Option Precedence

An option given on the command line overrides its default. A repeated value option takes its last value, including a global option given both before and after the subcommand; `-v` and `-q` count from both positions. `--log-level` sets the starting level, then each `-v` raises it and each `-q` lowers it by one, in any order. `--help` and `--version` take precedence over every other option and over a missing subcommand. Settings are supplied only through command-line options; there is no configuration file or environment-variable configuration.

#### Invalid Combinations

Each of these is a usage error with exit status 2, reported before any lane or TCP socket opens.

- No subcommand, or a subcommand other than `tx`, `tx-pat`, `rx` or `check-pat`.
- A command option before the subcommand.
- An option of one subcommand with another subcommand; `--remote` belongs to both `tx` and `tx-pat`, `--bytes` belongs to `tx-pat` only and `--ipd` to `rx` only.
- More than one `INPUT` operand, or `--listen` together with an `INPUT` operand.
- `--lanes` below 1, a port outside 1 to 65535, or base port + N - 1 above 65535.
- `--listen` with a non-loopback address.
- `--datagram-size` out of range, or `--rx-memory` that gives W below 1 or at least half the sequence space, 2^(S-1). W is computed from the effective datagram size. An `--rx-memory` that no datagram size from 25 to 65507 could accept is rejected before the adapter MTU is read; otherwise, when the size is derived from the adapter MTU, the error follows the S-25 line.
- A missing, malformed, negative or non-numeric option value, including a byte count outside its grammar or above 2^64 - 1, and an `--ipd` value outside its grammar, of 0 or above 2^64 - 1 ns.

#### Usage Examples

These examples are illustrative; each comment states the expected result. Back-to-back verification loop on one host, with every default (four terminals; `nc` stands for any TCP client and sink):

```sh
nc -l 127.0.0.1 31200 > received.bin    # sink for the reconstituted stream
socket-mux rx                           # binds UDP 127.0.0.1:31000, connects to 127.0.0.1:31200
socket-mux tx                           # listens on 127.0.0.1:31100, sends to 127.0.0.1:31000
nc 127.0.0.1 31100 < original.bin       # source stream
cmp original.bin received.bin           # equal when RX delivered every datagram TX sent (S-09, S-22)
```

The same loop with `tx` reading a file, then standard input, instead of a TCP client:

```sh
socket-mux tx original.bin              # reads the file
cat original.bin | socket-mux tx -      # reads standard input
```

A pattern loop with a fixed seed that ends by itself after 1 GB, followed by `check-pat` validating the saved output:

```sh
nc -l 127.0.0.1 31200 > received.bin
socket-mux rx                                   # exits 0 after the end-of-stream datagram
socket-mux tx-pat --seed 42 --bytes 1G          # exits 0 after 1 GB and end of stream
socket-mux check-pat --seed 42 < received.bin
```

Two hosts with two lanes; RX at 192.0.2.10 delivers to a local service on port 8080 and requests a 64 MiB UDP receive buffer, while TX keeps the operating-system default send buffer ([UDP Socket Buffer Sizing](design.md#udp-socket-buffer-sizing)). On Linux the receive request is capped at `net.core.rmem_max`, which S-19 reports:

```sh
socket-mux -n 2 --udp-buffer 64Mi rx --bind 0.0.0.0 --connect 127.0.0.1:8080   # on 192.0.2.10
socket-mux -n 2 tx --listen 127.0.0.1:18080 --remote 192.0.2.10                 # on the sending host
```

The same two hosts sending 3 GB of pattern with debug logging, with RX allowing 2 ms of inter-packet delay; at about 820,000 datagrams/s the window rule needs W of at least about 1640 datagrams, which the default 64 MiB RX memory limit (W = 46218) exceeds with room for the TCP reader's backlog:

```sh
socket-mux -n 2 --udp-buffer 64Mi rx --bind 0.0.0.0 --ipd 2ms   # on 192.0.2.10
socket-mux -v -n 2 tx-pat --remote 192.0.2.10 --bytes 3G        # on the sending host
```

## Invariants

- N must be at least 1.
- Each lane must use a different port.
- Every UDP datagram must carry the datagram header.
- Neither mode retransmits a lost datagram.
- `tx` reads exactly one input: one TCP connection on localhost, standard input (`-`) or one file.
- `tx-pat` reads no input stream; it generates the pattern and sends it under the same port and header rules as `tx`.
- `tx-pat` uses a random seed unless an option sets a fixed seed.
- RX's output from a pattern loop must be checkable against the pattern from any point after a loss stretch, under any pattern of UDP datagram loss, including adversarial loss.
- RX delivers strictly in sequence order and never delivers a datagram out of sequence ([Inter-Packet Delay](design.md#inter-packet-delay)).
- While RX holds a datagram or a settled sequence number, or has dropped no datagram under the buffer rule since its last delivery, it never waits for a missing next beyond its deadline: at the first instant after the deadline it declares the missing run lost or ends the stream ([loss rules](#semantics)). Otherwise it ends the stream once ipd has passed since its last buffer-rule drop. A delivered datagram waits only for the TCP output, which the RX memory limit bounds.
- TX sends each datagram as soon as its lane accepts it and never delays a datagram to pace the stream ([No TX Pacing](design.md#no-tx-pacing)).
- No socket-mux thread polls a socket: every socket send and receive wait is a blocking call ([Wait Policy](design.md#wait-policy)).
- A socket-mux thread that waits for work spins for at most a bounded time on the order of nanoseconds to microseconds, then backs off by yielding, then by sleeping for increasing times up to a cap, then by blocking until woken, so an idle `tx`, `tx-pat` or RX, and an RX holding datagrams behind a gap, uses approximately 0 % CPU ([Wait Policy](design.md#wait-policy)).
- Loss and summary reporting never delays receiving, ordering, delivering, writing or sending: no thread that does that work formats a report line or waits for the report queue, and when the report queue is full, RX discards the newest report entry and counts it ([Loss And Summary Reporter](design.md#loss-and-summary-reporter)).
- A stalled TCP output does not stop RX receiving datagrams from its lanes; once every RX buffer is in use, the buffer rule drops arrivals as `window` loss and releases the gaps before held datagrams ([Thread-Per-Lane Blocking I/O](design.md#thread-per-lane-blocking-io)).

## Contracts

### Datagram Header

The header that every datagram carries ([Header Per UDP Datagram](design.md#header-per-udp-datagram)) has this layout ([Datagram Header Layout](design.md#datagram-header-layout)). It is always 24 bytes, followed by `payload_len` bytes of slice data. Multi-byte fields use network byte order (big-endian). The sequence wire field is u64 even in reduced-width rollover-test builds. Version remains 1 throughout pre-alpha wire changes; version bumps begin with formal releases. There is no per-datagram application checksum.

| Field         | Offset (bytes) | Size (bytes) | Byte order | Purpose                                                                                                               |
| ------------- | -------------- | ------------ | ---------- | --------------------------------------------------------------------------------------------------------------------- |
| magic         | 0..2           | 2            | network    | Constant `0x534D` ("SM"); marks a socket-mux datagram.                                                                |
| version       | 2              | 1            | n/a        | Header format version, 1.                                                                                             |
| flags         | 3              | 1            | n/a        | Bit 0 = end of stream; bits 1 to 7 are zero.                                                                          |
| payload_len   | 4..6           | 2            | network    | Number of slice-data bytes after the header.                                                                          |
| session       | 6..8           | 2            | network    | Random 16-bit ID for this TX run.                                                                                     |
| sequence      | 8..16          | 8            | network    | Global slice sequence number across all N lanes: 0 for the first slice, one more modulo 2^S for each following slice. |
| stream_offset | 16..24         | 8            | network    | Byte offset of this slice's first byte in the original stream, modulo 2^64; it rolls over like the sequence number.   |

The datagram size includes this header. At a 1500-byte adapter MTU the default datagram size is 1452 bytes, leaving 1452 - 24 = 1428 payload bytes, and at the default 64 MiB RX memory limit W = floor(67108864 / 1452) = 46218 datagram buffers, so RX's datagram buffers occupy at most 64 MiB.

## Semantics

- Session ([Session Identity And Restart](design.md#session-identity-and-restart)): TX (`tx` and `tx-pat`) chooses a random 16-bit session ID at start, logs `session=<n>` at `debug`, and carries that ID in every datagram, including end of stream. RX locks onto the session of its first valid datagram. A valid datagram from a different session makes RX abort, so that two sessions are never conflated in one output: RX logs an `error` (S-18), stops writing to its TCP output and closes it without delivering the datagrams it holds or has not yet written, declares no further loss, prints its final summary and exits with status 1, a runtime failure ([Exit Status](#exit-status)). It does not deliver the different session's payload. A new stream requires a fresh RX process; there is no resume. A repeated session ID cannot distinguish runs, and the first valid datagram may belong to a stale session ([known limits](known-issues.md#register)).
- Ports ([RX Listen Ports](design.md#rx-listen-ports)): lane k, for k from 0 to N - 1, uses base port + k on both sides. TX sends lane k to `--remote` at base port + k; RX listens on the same ports. The operator supplies both sides the same lane count, base port and datagram size by hand; there is no negotiation.
- Loss: RX determines packet loss and the length of that loss from the datagram headers. The sequence gap gives the lost slice count and the stream-offset gap gives the lost byte length; RX skips the lost bytes, keeps the order of the bytes it delivers, and counts the loss stretch with its cause in its loss report (S-09). RX declares a missing sequence number lost only under the ipd rule or the window rule below, and drops an arriving datagram as lost only under the buffer rule; a dropped datagram's lost byte length is its payload length.
- Input: `tx` splinters its input across the N UDP lanes, and RX reassembles it on the remote end, so `tx` and RX act like a netcat split over N UDP lanes. `tx` accepts `-` (standard input) or a file as its input.
- Pattern: `tx-pat` generates a sequence of 4096-byte blocks, starting at block index 0. Each block contains an 8-byte big-endian index starting at zero, 4084 bytes of SplitMix64 payload keyed by the seed and index, and a 4-byte big-endian Adler-32 checksum of the first 4092 bytes. The SplitMix64 state starts at `seed XOR (index × 0x9E3779B97F4A7C15)` with wrapping 64-bit multiplication; each output step adds `0x9E3779B97F4A7C15`, applies the SplitMix64 mixing operations, and emits the result big-endian, truncating the last output to four bytes. Adler-32 starts with A = 1 and B = 0, uses modulus 65521, and stores `(B << 16) | A`.
- Pattern length (S-20): without `--bytes`, `tx-pat` runs until a send error or a signal and sends no end-of-stream datagram. With `--bytes N`, it sends exactly the first N bytes of the pattern, so the last block may be partial, then marks its final datagram with the end-of-stream flag, prints its final summary and exits 0.
- Start of stream: RX waits without a limit for its first valid datagram and locks onto its session. The loss rules below then apply within that session, starting with next at 0, the sequence number of the session's first slice, and the last-delivery time at the arrival of that first datagram. Sequence numbers below the first one to arrive are ordinary missing sequence numbers, so an RX started after its TX has begun counts the stream's earlier part as lost.
- Loss rules ([Inter-Packet Delay](design.md#inter-packet-delay)): RX applies the rules below to each arrival in the order listed, and takes arrivals and deadlines in time order: an arrival at or before a deadline is processed before that deadline expires, and an expired deadline is resolved before any later arrival, so which arrivals fall within ipd depends only on arrival times ([Terminology](#terminology)), never on when RX processes them.
  - Late and duplicate: an arriving datagram whose sequence number s is before next is late, when RX declared s lost, or a duplicate, when RX delivered it; RX tells the two apart for the W sequence numbers before next and counts an older one as late. One whose s RX already holds is a duplicate, and one whose s is settled is late. RX drops it and counts it in the loss report.
  - Window rule: an arriving datagram whose s is at or after next + W does not fit. RX declares the run of missing sequence numbers from next to the lowest held or settled sequence number, or to s when it holds neither, lost as one loss stretch, cause `window`, passes the settled sequence numbers and delivers the held run that follow as the hold-and-deliver rule does, and repeats until s is below next + W. Passing settled sequence numbers counts no further loss, and when no datagram is delivered the last-delivery time is unchanged.
  - Buffer rule: when every RX buffer is in use as the datagram arrives, RX drops that arriving datagram, never one it already holds, counts s lost, cause `window`, at once, and marks s settled. The dropped datagram is an arrival for the ipd rule; it is not delivered, so it leaves the last-delivery time unchanged. When s is next, next passes it, and RX delivers the held run that follows as the hold-and-deliver rule does. The drop puts RX under buffer pressure ([Terminology](#terminology)). Under buffer pressure RX does not wait for ipd at a missing next after which it holds a datagram: it declares the run of missing sequence numbers from next to the lowest held or settled sequence number lost as one loss stretch, cause `window`, passes the settled sequence numbers and delivers the held run that follow, and repeats while the pressure lasts and it holds a datagram after a missing next. When it holds none, as when every buffer holds a datagram awaiting its TCP write, the drop is the rule's only effect. Because datagrams awaiting their TCP write keep their buffers, a reader of RX's TCP output slower than the stream also causes `window` loss under this rule.
  - Hold and deliver: RX holds the arriving datagram, then delivers the contiguous run of held datagrams from next in sequence order, passing the settled sequence numbers within it. Next becomes the sequence number after the run, and the last-delivery time becomes the arrival time of the run's last delivered datagram.
  - Ipd rule: while next is missing, RX waits until the deadline; an arrival at or before the deadline is within ipd. At the first instant after the deadline, if RX holds a datagram or a settled sequence number, which means datagrams arrived while it waited, it declares the run from next to the lowest held or settled sequence number lost as one loss stretch, cause `ipd`, passes the settled sequence numbers that follow, delivers the held run that follows, and applies this rule again with the new deadline. If RX holds neither and has dropped no datagram under the buffer rule since its last delivery, nothing arrived while it waited, the stream is over and RX ends it. If RX holds neither but has dropped a datagram under the buffer rule since its last delivery, that datagram arrived within ipd, so the stream stays open while such drops keep arriving within ipd of one another: RX ends the stream at the first instant after the deadline at which it holds neither and ipd has passed since its last buffer-rule drop. The deadline itself still counts from the last-delivery time.
  - End-of-stream rule: delivering the end-of-stream datagram ends the stream at once.
- Loss stretches: the ipd rule declares a whole run of missing sequence numbers lost as one stretch after one ipd, not after one ipd per missing datagram ([Inter-Packet Delay](design.md#inter-packet-delay)). The same rules apply to every later gap.
- Worked examples, with ipd = 2 time units (illustrative):
  - Datagrams 0 to 3 arrive in sequence by t = 4 and are delivered; 4 to 9 arrive at t = 5 and are delivered, so the last-delivery time is 5 and the deadline 7. Datagram 10 is missing. If 11 arrives by t = 7, within ipd, then at the first instant after 7 RX declares 10 lost, a stretch of 1 with cause `ipd`, delivers 11 and the run after it, and the stream continues; 10 arriving at t = 15 is late. If instead nothing arrives by t = 7, the stream is over just after t = 7, and RX ends it without its end-of-stream datagram. Expiry of ipd ends the stream only when nothing arrived while RX waited.
  - Datagrams 100 to 104 are lost on the link and 105 arrives at t = 0, just after 99 was delivered at t = 0. Just after t = 2, RX declares 100 to 104 lost as one stretch of 5, cause `ipd`, and delivers 105: the five losses cost one ipd, not five.
  - The first datagram of the session to arrive is 2, at t = 0. If 0 and 1 arrive by t = 2, RX delivers 0, 1 and 2 in order. If only 1 arrives by t = 2, then just after t = 2 RX declares 0 lost, cause `ipd`, and delivers 1 and 2.
  - With W = 8, next = 20 is missing and 21 to 27 are held when 28 arrives within ipd. 28 is at next + W, so RX declares 20 lost, cause `window`, delivers 21 to 27, then holds and delivers 28.
- End of stream: `tx` marks its final datagram with the end-of-stream flag after its input ends, and `tx-pat --bytes` after its last pattern byte. The end-of-stream datagram carries a sequence number and a payload of zero or more bytes, and RX processes it only in sequence order. A stream also ends when the ipd rule ends it, whether or not its end-of-stream datagram was lost; RX then logs that the stream ended without it, and its final summary states so (Diagnostics). The sequence numbers TX sent after the last datagram RX received cannot be known to RX and are not counted as lost; the [total error rate](#terminology) counts them. When its stream ends, RX completes the TCP writes of the datagrams in its writer staging, closes its TCP output, prints its final summary and exits 0.
- Sizing: ipd and W are separate settings. RX holds at most the datagrams that arrive within ipd of a gap, so W must be at least the arrival rate in datagrams per second times ipd, or the window rule declares loss before ipd: at about 9.4 Gbit/s of 1452-byte datagrams, about 820,000 datagrams/s, ipd = 1 ms needs W of at least about 820 datagrams, an RX memory limit of about 1.2 MB. RX's buffers also hold the datagrams awaiting their TCP write, so the RX memory limit must also cover the TCP reader's backlog, or the buffer rule drops arrivals as `window` loss. ipd must exceed the largest out-of-sequence delay of the link, or RX declares reordered datagrams lost and then drops them as late; RX reports that delay (S-09) so that ipd can be set from measurement.
- Backpressure: TX sends with no delays and waits only for each of its own UDP sends to complete; RX sends no backpressure to TX. socket-mux assumes that the program feeding TX and the program reading RX's TCP output keep up with the stream or buffer their own processing delays. A pause in TX's input longer than ipd therefore ends RX's stream under the ipd rule, and a TCP reader slower than the stream keeps RX's buffers in use, after which the buffer rule drops arrivals as `window` loss and declares the gaps before held datagrams lost without waiting for ipd; RX does not tell that loss apart from a window too small for the arrival rate. There is no separate output-stall or silence timeout.
- Sequence numbers: they always roll over, modulo 2^S, and RX compares them with serial-number arithmetic: s is after next when (s - next) mod 2^S is below 2^(S-1), and before next when it is above. RX tolerates no sequence ambiguity: a gap of half the sequence space, 2^(S-1), is a fatal error, and RX logs it and exits with status 1. W must therefore be below 2^(S-1). The stream offset rolls over the same way, modulo 2^64, and RX computes the stream-offset gap of a loss modulo 2^64.
- Loss report (S-09): from its first valid datagram until its stream ends, RX reports loss only through loss warnings at `warn`, at every log level, and prints nothing at `info`; when it ends, it prints one final summary at `info`, covering the whole run, its only `info` line. Lost-slice and lost-byte counts are exact. Loss stretches and out-of-sequence delays reach the reporter only as compact entries through one bounded wait-free queue of 4096 entries, which the reporter drains as fast as it can: one entry per loss stretch RX declares, and one per datagram RX delivers with an out-of-sequence delay, carrying that delay and the datagram's arrival time; a delivery without an out-of-sequence delay pushes no entry. When that queue is full, the newest entry is discarded and counted as dropped (`events_dropped`): a discarded stretch's slices still count as lost, and the stretch count, the longest stretch, the out-of-sequence count and the largest out-of-sequence delay cover the received entries only, so with dropped entries the out-of-sequence count is a lower bound, which `events_dropped` reveals. The reporter groups the loss stretches it drains by reporting period, and after a period with at least one loss-stretch entry ends, it prints one loss warning for that period; a period without such an entry prints nothing. Whether a stretch belongs to the period in which RX declared it lost or to the period in which the reporter drained its entry, and where the span of the warning for the period in which RX ends stops, are a gap. A stretch whose entries fall in two periods counts as a stretch in each. A warning's lost slices and lost bytes are those of its period's entries, and the warnings sum to the final summary's exact totals only when no entry was dropped. When RX ends, the reporter drains the queue, prints the warning of every period with loss not yet reported, then prints the final summary. RX prints no out-of-sequence delay per datagram at any log level; the reporter counts the out-of-sequence delay entries it receives and keeps the largest delay among them, and the final summary reports both.
- Report units: byte counts and rates count payload bytes only, in decimal units with three significant digits (1 GBytes is 10^9 bytes, 1 Gbit/s is 10^9 bits per second); a byte count below 1000 is printed exactly, as `512 Bytes`. The RX final summary spans from the arrival of the first valid datagram to the completion of the last TCP write; the TX final summary spans from TX framing its first datagram to the completion of its last send.
- TX report (S-22): `tx` and `tx-pat` print no interval report at any level, and one final summary at `info` when they end: after end of stream, on a send error and on SIGINT or SIGTERM.
- Signals (S-23): on SIGINT or SIGTERM, `tx`, `tx-pat` and RX stop, print every loss and summary fact recorded so far in their final summary, and exit with status 130 for SIGINT and 143 for SIGTERM. On Windows, Ctrl-C has the SIGINT effect and status, and closing the console has the SIGTERM effect and status. After such a signal TX sends no end-of-stream datagram, and RX stops writing to its TCP output: datagrams it still holds or has not yet written are not delivered, and it closes that connection. A second SIGINT or SIGTERM ends the process at once with the status of the first. A process that has not ended 2 s after the first signal, for example `tx` waiting for terminal input on standard input, prints its final summary if it has not yet done so and exits with that status.
- Datagram size and MTU: without `--datagram-size`, each side's datagram size is its adapter MTU ([Terminology](#terminology)) less 48 bytes (the 40-byte IPv6 and 8-byte UDP headers), limited to the range 25 (the 24-byte header and one payload byte) to 65507, so one datagram fits one frame of that adapter; when the adapter MTU cannot be read, the default is 1452. `--datagram-size` overrides the default and accepts 25 to 65507 bytes. Each side logs its effective datagram size and its source once at start (S-25). When the datagram size exceeds the adapter MTU less 48, the side also logs one warning (S-24) and proceeds. A datagram larger than the path MTU less 48 bytes is fragmented by IP, and losing one fragment loses the whole datagram; a smaller MTU elsewhere on the path draws no warning ([known issues](known-issues.md#register)). The two sides derive their defaults from different adapters, and RX discards a datagram larger than its own datagram size, so where the two adapter MTUs differ the operator gives both sides the same `--datagram-size`.
- Verification loop: TX and RX can be placed back to back in a verification loop, with either `tx` or `tx-pat` as TX.

## Validation

- Pattern verification: `check-pat` reads RX's output from standard input. It finds valid 4096-byte windows by Adler-32 and, when `--seed` is given, also regenerates and compares the payload. It accepts a block whose index follows the prior accepted index; otherwise it searches forward one byte at a time for the next valid window and reports resynchronization. Without a seed, it checks the checksum and index order but cannot verify the pseudorandom body.
- Checker report: one line is printed in the form `check-pat: blocks_ok=<n> blocks_bad=<n> resyncs=<n> lost_bytes=<n> skipped_bytes=<n> trailing_bytes=<n> first_index=<index|none> last_index=<index|none>`. It reports valid and bad blocks, resynchronizations, inferred missing bytes, bytes skipped while searching, bytes after the last complete valid block, and first/last accepted indices; absent indices are `none`. A `tx-pat --bytes` run whose N is not a multiple of 4096 leaves a partial final block, which `check-pat` counts as trailing bytes.

## Diagnostics

TX and RX print diagnostics through their log on standard error, at the levels below; `--log-level`, `-v` and `-q` select which levels appear. At `info`, TX and RX print only their final summary, at the end of the stream; start-up and end facts outside the summary print at `debug`, and while a stream runs RX reports loss only through loss warnings. Each diagnostic is one log line; the logger begins it with a bracketed UTC timestamp in milliseconds, the level and the module, for example `[2026-10-30T00:31:09.432Z INFO  socket_mux::rx]`, and the text below follows. In the formats below, `<span>` is `[<from>-<to> s]` with each time in seconds to two decimals, padded to five characters; `<bytes>` is a byte count such as `1.17 GBytes`; `<rate>` is a rate such as `9.38 Gbit/s`; `<delay>` is the largest out-of-sequence delay of the run, written compactly as a number followed directly by its unit: below 1000 ns, the whole number of nanoseconds and `ns`; otherwise three significant digits and the largest of the units `us`, `ms` and `s` in which the delay is at least 1, such as `850ns`, `41.2us` or `1.50ms`; `0ns` when no datagram RX delivered had an out-of-sequence delay. `<session>` is the session ID, the same number as S-17 prints; in the RX final summary it is the session RX locked onto, or `none` when RX ended before it locked onto one. `<reason>` states why RX ended: `eos` when it delivered the end-of-stream datagram, `ipd` when the ipd rule ended the stream without it, `signal` on SIGINT or SIGTERM, and `error` on a runtime failure, including a datagram of a different session, which exits with status 1.

- UDP buffer (S-19): once per side, `--udp-buffer` logs `udp buffer requested=<n> effective=<m>` at `debug`. The effective size is the socket readback divided by two on Linux, unchanged elsewhere. If effective < requested, RX or TX warns that the OS capped it; on Linux the warning names sysctl `net.core.rmem_max` (RX) or `net.core.wmem_max` (TX). Without the option, the OS-default effective size is logged at `debug`. Capping is not an error.
- Datagram size above adapter MTU (S-24): trigger: TX or RX starts with a datagram size above its adapter MTU less 48 bytes; facts: the datagram size, the adapter MTU and that datagrams of this size fragment; at `warn`, once per side, then the side proceeds. No warning is logged when the adapter MTU cannot be read. The line reads `datagram size <size> exceeds <adapter> mtu <mtu> less 48; datagrams will be IP-fragmented and a lost fragment loses the datagram`.
- Datagram size (S-25): trigger: TX or RX starts; facts: the effective datagram size and its source, at `debug`, once per side: `datagram size <size> (<adapter> mtu <mtu>)` for a size derived from the adapter MTU, with `; clamped` before the closing parenthesis when the 25 to 65507 limit changed it; `datagram size <size> (--datagram-size; <adapter> mtu <mtu>)` or `datagram size <size> (--datagram-size; mtu unknown)` for a given size; and `datagram size 1452 (default; mtu unknown)` when no size is given and the adapter MTU cannot be read.
- Session (S-17): trigger: `tx` or `tx-pat` starts, or RX locks onto the session of its first valid datagram; facts: `session=<n>`, the session ID; at `debug`.
- New RX session (S-18): trigger: RX receives a valid datagram with a session ID different from its locked session; facts: `new session <n> (current <m>); aborting`; at `error`, then RX aborts under the session rule: it delivers nothing more, prints its final summary and exits 1.
- Loss warning (S-09): trigger: a reporting period with at least one loss-stretch entry ends, or RX ends with such a period not yet reported ([loss report](#semantics)); facts: the period as a span from the arrival of the first valid datagram, and over that period's loss-stretch entries the lost slices and lost bytes, the number of loss stretches and lost slices per loss cause; at `warn`, once for that period, as `loss <span> lost <x> datagrams <y> bytes in <k> stretches (ipd <i> window <w>)`, for example `loss [ 3.00- 4.00 s] lost 15 datagrams 21420 bytes in 2 stretches (ipd 12 window 3)` (illustrative). TX and RX print no interval report at any level.
- RX final summary (S-09): trigger: RX ends after it connected its TCP output, by delivering the end-of-stream datagram, by the ipd rule, by a different session, on SIGINT or SIGTERM, or on another runtime failure; facts: the session ID, the run's span, payload bytes delivered and average rate, delivered bytes and datagrams, lost slices and lost bytes, the number of loss stretches, lost slices per loss cause, the longest loss stretch, late and duplicate datagrams dropped, the out-of-sequence count (the datagrams RX delivered with an out-of-sequence delay, counted from the received entries) and the largest out-of-sequence delay of the run, when nonzero the dropped report entries, and why RX ended; at `info`, as `rx summary: session <session>  <span>  <bytes>  <rate>  delivered <b> bytes in <d> datagrams  lost <x> datagrams <y> bytes in <k> stretches (ipd <i> window <w>) longest <l>  late <a> duplicate <u>  oos <o> oos_delay <delay>`, followed by `  events_dropped <e>` when e is above 0, and ending with `  end <reason>`.
- RX ended without end of stream: trigger: the ipd rule ends the stream; facts: the effective ipd and the run's lost slices and lost bytes; at `debug`, as `ipd <ipd> passed with no datagram held; stream ended without its end-of-stream datagram: total_lost_slices=<n> total_lost_bytes=<n>`, with `<ipd>` written as an integer in the largest of the units `ns`, `us`, `ms` and `s` that represents it exactly, such as `1ms` or `1500us`. A different session logs the S-18 line and a signal the S-23 line; an end of stream by the end-of-stream datagram logs no separate line.
- TX final summary (S-22): trigger: `tx` or `tx-pat` ends after end of stream, on a send error or on SIGINT or SIGTERM; facts: the session ID, for `tx-pat` the seed, the run's span, payload bytes sent and average payload rate, and payload bytes and datagrams sent; at `info`, as `tx summary: session <session>  <span>  <bytes>  <rate>  sent <b> bytes in <d> datagrams` for `tx`, and with `session <session> seed <seed>` in place of `session <session>` for `tx-pat`, where `<seed>` is the seed in decimal, the value `--seed` accepts. A send error is logged at `error`; a signal logs the S-23 line.
- Signal (S-23): trigger: the first SIGINT or SIGTERM; facts: `received SIGINT; stopping` or `received SIGTERM; stopping` at `debug`; when the process has not ended 2 s later, `did not stop within 2s; exiting` at `warn`.
- Sequence ambiguity: trigger: a gap of half the sequence space; facts: next and the received sequence number; at `error`, then exit status 1.
- Exit status: see [Exit Status](#exit-status).

## Boundaries

- Throughput and error rate: socket-mux makes no zero-loss guarantee at any rate; datagram loss is normal on its lossy channel. The success of a transfer, including a qualification run, is judged by its total error rate, not by the absence of loss. On a 10 Gbit/s link through a single switch the target delivered fraction is three to five nines, 99.9 % to 99.999 %, so a run on such a link that delivers less than 99.9 % misses the target. On a 10GbE path near line rate, the receiving host's network adapter can drop rare datagrams before RX sees them ([known issues](known-issues.md#register)).
- Platforms ([First-Release Platform Targets](design.md#first-release-platform-targets)): the first-release (MVP) qualification scope is Linux x86_64 with a static musl build. Qualification requires both a file transfer and a `tx-pat`/`check-pat` run to pass on a real target machine; a successful cross-build alone is not a pass. A qualification run passes when its delivered fraction meets the error-rate target; a file transfer is judged by that target, not by equal checksums of the sent and received files, because a lossy run's output differs from its input. Linux x86_64 was qualified on the code of commit `908a81d`: on two Linux x86_64 hosts over 10GbE, file transfers and pattern runs at one and four lanes in both directions each delivered at least 99.999 % of the datagrams sent, and 68 of the 72 runs of a link sweep delivered at least 99.995 %; the other 4 sweep runs fell in events of known issue `KI-13` ([known issues](known-issues.md#register)) and delivered 22 % to 99 % ([Measured Link Behavior](design.md#measured-link-behavior)). That code applies a 10 s silence timeout and memory-limit loss rules in place of the loss rules, `--ipd` and writer staging this specification states, and has TX pacing, so its qualification does not cover them; Linux x86_64 is not yet qualified on code that realizes them. Linux aarch64 is built but not tested; qualification is deferred. Windows 10/11 x86_64 is built but not yet qualified; qualification is next, pending the Windows peer. macOS was tested on an earlier build without a recorded version or architecture; the current build has not been re-tested on macOS, and that re-test is deferred.
- Security ([Trusted-Link Security Boundary](design.md#trusted-link-security-boundary)): socket-mux is for trusted or private links only. Lane traffic is neither encrypted nor authenticated: anyone on the path can read it, and anyone who can reach RX's UDP ports can inject datagrams. To cross an untrusted network, run socket-mux inside a VPN, for example WireGuard. Session IDs are not authentication.
- Retransmission is out of scope at this stage.
