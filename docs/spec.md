# socket-mux Specification

## Purpose

Define the consumer-visible behavior of socket-mux: its TX and RX modes and four subcommands, its command-line interface, the input TX accepts or generates, the UDP lanes and per-datagram header it uses, the stream it reconstitutes, how it reports loss and throughput, how it ends on a signal, its configurable lane count and the platforms it supports. This specification defines the ratified intended baseline for the socket-mux CLI, including its TX and RX modes and the `check-pat` subcommand; it does not assert that every specified behavior is implemented in any particular source revision. "Must" marks a requirement. "Gap" marks behavior this specification does not define; and a consumer relies on no particular behavior there.

## Terminology

| Term               | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TX                 | Transmit mode, run by the `tx` or the `tx-pat` subcommand. It splinters its input into N UDP lanes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `tx` input         | The input of the `tx` subcommand: one TCP connection on localhost, standard input (`-`) or a file.                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Pattern            | The continuous pseudorandom pattern that `tx-pat` generates as its input, also called an "adler pattern".                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Seed               | The value from which `tx-pat` generates the pattern: random by default, or a fixed seed set by an option.                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| RX                 | Receive mode. It receives the N UDP lanes and reconstitutes the original stream.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| N                  | The number of UDP lanes, which is also the number of slices.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Lane               | One of the N UDP datagram flows from TX to RX; each uses a different port.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Slice              | A part of the original stream carried in one UDP datagram; the header sequences slices on reconstitution.                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Base port          | The first port of the N lane ports; lane k (0 to N-1) uses base port + k.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Session            | One TX run, identified by a random 16-bit session ID chosen at start and carried in every datagram header. RX accepts one session per process.                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Datagram header    | The header every UDP datagram carries.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Timeout T          | RX's one timeout, set by a global command-line option, default 10 s; spelled `--timeout` ([Inter-Packet Delay Timeout Spelling](design.md#inter-packet-delay-timeout-spelling)). It is also called the inter-packet delay timeout.                                                                                                                                                                                                                                                                                                                                    |
| Loss stretch       | A run of consecutive slices that RX declares lost with one cause; consecutive runs of the same cause count as one stretch. Its length is its count of lost slices, for example 15 datagrams lost.                                                                                                                                                                                                                                                                                                                                                                     |
| Loss cause         | Why RX declared a loss stretch: `timeout` (rule A or B), `memory` (RX memory limit) or `output` (output limit).                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Datagram size      | The size of every UDP datagram, header included, set by a global option.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Adapter MTU        | The MTU of the network adapter a side uses. For TX it is the adapter that owns the local address the operating system selects to reach the first address `--remote` resolves to. For RX it is the adapter that owns the `--bind` address; when `--bind` is `0.0.0.0` or `::`, it is the largest MTU among the adapters that are up, have a readable MTU, are not loopback and have an address of that family (an IPv4 address for `0.0.0.0`, any address for `::`); a loopback adapter that meets the other conditions counts only when no non-loopback adapter does. |
| UDP socket buffer  | The bytes the operating-system kernel queues for one lane socket: on RX the received datagrams waiting for RX to read them, on TX the datagrams waiting to be sent. It is unrelated to `tx-pat --bytes`, the bytes `tx-pat` sends.                                                                                                                                                                                                                                                                                                                                    |
| RX memory limit    | The maximum receive memory RX may use for datagrams it holds out of order or has not yet written to its TCP output; set by a global option.                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Hold capacity W    | The number of datagrams that fit in the RX memory limit: RX memory limit ÷ datagram size, rounded down.                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Sequence width S   | The effective bit width of the sequence counter, a build constant: 64 in normal builds, 8 or 16 in builds that test rollover. The wire field remains u64 at every width.                                                                                                                                                                                                                                                                                                                                                                                              |
| Next               | The lowest sequence number RX has neither delivered nor declared lost.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Arrival time       | The time RX's application dequeues a datagram from its socket, read from a monotonic clock; not a kernel timestamp.                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Interval report    | One line TX or RX prints at the end of each reporting interval (`--interval`) while a stream runs, in the manner of iperf3.                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Final summary      | One summary line TX or RX prints when it ends, covering the whole run.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Pacing interval    | The `tx-pat --ipd-ns` value: the time between the due times of consecutive datagrams across all lanes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Verification loop  | TX and RX placed back to back; a pattern loop is `tx-pat` and RX placed back to back.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Total error rate   | The share of a run's datagrams that RX did not deliver: the datagrams TX sent less the datagrams RX delivered, over the datagrams TX sent, taken from the TX final summary (S-22) and the RX final summary (S-09) of the same run. It counts every lost datagram, including a lost tail that RX never declared lost.                                                                                                                                                                                                                                                  |
| Delivered fraction | The datagrams RX delivered over the datagrams TX sent, one minus the total error rate; three nines is 99.9 % (a total error rate of 10^-3) and five nines is 99.999 % (10^-5).                                                                                                                                                                                                                                                                                                                                                                                        |

## Model

TX reads one input and splinters it into N UDP lanes, each on a different port, with a header on every datagram. The `tx` subcommand reads one TCP connection on localhost, standard input (`-`) or a file, like netcat, and RX reassembles that stream on the remote end. The `tx-pat` subcommand behaves as `tx` does, except that its input is a pattern it generates instead of an input stream, optionally paced and optionally limited to a byte count. The `check-pat` subcommand reads a pattern stream from standard input and validates it; it opens no socket. RX uses the headers to sequence slices and to determine packet loss and the length of that loss, and reconstitutes the original stream. Neither network mode retransmits, so the channel is lossy. RX reports throughput and loss as summarised interval and final lines, never per datagram at the default log level; TX reports its sent throughput the same way.

```text
TCP client (127.0.0.1:31100), standard input or file -> tx -> UDP base port .. base port + N - 1 -> RX -> TCP peer (127.0.0.1:31200)
generated pattern                                      -> tx-pat -> UDP base port .. base port + N - 1 -> RX -> TCP peer -> pattern validation
```

The ports in the diagram are the defaults ([Default Ports](design.md#default-ports)).

### Command Line

#### Grammar

The binary is `socket-mux` with this grammar ([Command-Line Options](design.md#command-line-options)). socket-mux is a CLI with TX and RX subcommands and a `tx-pat` subcommand ([One Program With TX And RX Subcommands](design.md#one-program-with-tx-and-rx-subcommands)). `tx` takes an optional `INPUT` operand ([TX Input Operand](design.md#tx-input-operand)).

```text
socket-mux [GLOBAL OPTIONS] tx [GLOBAL OPTIONS | TX OPTIONS]... [INPUT]
socket-mux [GLOBAL OPTIONS] tx-pat [GLOBAL OPTIONS | TX-PAT OPTIONS]...
socket-mux [GLOBAL OPTIONS] rx [GLOBAL OPTIONS | RX OPTIONS]...
socket-mux [GLOBAL OPTIONS] check-pat [GLOBAL OPTIONS | CHECK-PAT OPTIONS]...
socket-mux --help | --version
```

Global options are accepted both before and after every subcommand, including `check-pat`. Command options appear after the subcommand ([Command-Line Options](design.md#command-line-options)). TX sends lane k to `--remote` at base port + k, and RX listens on those same ports. The operator configures both sides with the same lane count, base port and datagram size by hand; they do not negotiate.

#### Check-Pat Options

`check-pat` reads standard input, takes no operand and opens no socket. With `--seed`, it also regenerates and checks each block body; without it, it checks Adler-32 and block-index order. It accepts the global options above and this command option:

| Long     | Short | Value                   | Default | Constraints                                 | Trace                                                                         |
| -------- | ----- | ----------------------- | ------- | ------------------------------------------- | ----------------------------------------------------------------------------- |
| `--seed` | `-s`  | unsigned 64-bit integer | none    | malformed value: usage error, exit status 2 | design [Check-Pat Checker Subcommand](design.md#check-pat-checker-subcommand) |

#### Option Precedence

An option given on the command line overrides its default. A repeated value option takes its last value, including a global option given both before and after the subcommand; `-v` and `-q` count from both positions. `--log-level` sets the starting level, then each `-v` raises it and each `-q` lowers it by one, in any order. `--help` and `--version` take precedence over every other option and over a missing subcommand. Settings are supplied only through command-line options; there is no configuration file or environment-variable configuration.

#### Invalid Combinations

Each of these is a usage error with exit status 2, reported before any lane or TCP socket opens.

- No subcommand, or a subcommand other than `tx`, `tx-pat`, `rx` or `check-pat`.
- A command option before the subcommand.
- An option of one subcommand with another subcommand; `--remote` belongs to both `tx` and `tx-pat`, and `--bytes` and `--ipd-ns` belong to `tx-pat` only.
- More than one `INPUT` operand, or `--listen` together with an `INPUT` operand.
- `--lanes` below 1, a port outside 1 to 65535, or base port + N - 1 above 65535.
- `--listen` with a non-loopback address.
- `--datagram-size` out of range, or `--rx-memory` that gives W below 1 or at least half the sequence space, 2^(S-1). W is computed from the effective datagram size. An `--rx-memory` that no datagram size from 25 to 65507 could accept is rejected before the adapter MTU is read; otherwise, when the size is derived from the adapter MTU, the error follows the S-25 line.
- A missing, malformed, negative or non-numeric option value.

#### Usage Examples

These examples are illustrative; each comment states the expected result. Back-to-back verification loop on one host, with every default (four terminals; `nc` stands for any TCP client and sink):

```sh
nc -l 127.0.0.1 31200 > received.bin    # sink for the reconstituted stream
socket-mux rx                           # binds UDP 127.0.0.1:31000, connects to 127.0.0.1:31200
socket-mux tx                           # listens on 127.0.0.1:31100, sends to 127.0.0.1:31000
nc 127.0.0.1 31100 < original.bin       # source stream
cmp original.bin received.bin           # equal when RX delivered every datagram TX sent (S-09, S-22)
```

The same loop with `tx` reading a file, then standard input, instead of a TCP client:

```sh
socket-mux tx original.bin              # reads the file
cat original.bin | socket-mux tx -      # reads standard input
```

A pattern loop with a fixed seed that ends by itself after 1 GB, followed by `check-pat` validating the saved output:

```sh
nc -l 127.0.0.1 31200 > received.bin
socket-mux rx                                   # exits 0 after the end-of-stream datagram
socket-mux tx-pat --seed 42 --bytes 1000000000  # exits 0 after 1 GB and end of stream
socket-mux check-pat --seed 42 < received.bin
```

Two hosts with two lanes; RX at 192.0.2.10 delivers to a local service on port 8080 and requests a 64 MiB UDP receive buffer, while TX keeps the operating-system default send buffer ([UDP Socket Buffer Sizing](design.md#udp-socket-buffer-sizing)). On Linux the receive request is capped at `net.core.rmem_max`, which S-19 reports:

```sh
socket-mux -n 2 --udp-buffer 67108864 rx --bind 0.0.0.0 --connect 127.0.0.1:8080   # on 192.0.2.10
socket-mux -n 2 tx --listen 127.0.0.1:18080 --remote 192.0.2.10                     # on the sending host
```

A paced pattern run with debug logging at a 1500-byte adapter MTU: 1428 payload bytes every 1500 ns is about 7.6 Gbit/s of payload:

```sh
socket-mux -v -n 2 tx-pat --remote 192.0.2.10 --ipd-ns 1500 --bytes 3000000000
```

## Invariants

- N must be at least 1.
- Each lane must use a different port.
- Every UDP datagram must carry the datagram header.
- Neither mode retransmits a lost datagram.
- `tx` reads exactly one input: one TCP connection on localhost, standard input (`-`) or one file.
- `tx-pat` reads no input stream; it generates the pattern and sends it under the same port and header rules as `tx`.
- `tx-pat` uses a random seed unless an option sets a fixed seed.
- RX's output from a pattern loop must be checkable against the pattern from any point after a loss stretch, under any pattern of UDP datagram loss, including adversarial loss.
- RX delivers strictly in sequence order and never delivers a datagram out of sequence ([Inter-Packet Delay Timeout](design.md#inter-packet-delay-timeout)).
- No datagram waits behind a gap longer than the timeout T. A datagram released in sequence order waits only for the TCP output; the RX memory limit, not T, bounds those ([loss limits](#semantics)).
- No socket-mux thread polls a socket: every socket send and receive wait is a blocking call ([Wait Policy](design.md#wait-policy)).
- A socket-mux thread that waits for work spins for at most a bounded time on the order of nanoseconds to microseconds, then backs off by yielding, then by sleeping for increasing times up to a cap, then by blocking until woken, so an idle `tx`, `tx-pat` or RX, and an RX holding datagrams behind a gap, uses approximately 0 % CPU ([Wait Policy](design.md#wait-policy)).
- Loss and summary reporting never delays receiving, ordering, delivering or sending: when the report queue is full, RX discards the newest loss-stretch report and counts it ([Loss And Summary Reporter](design.md#loss-and-summary-reporter)).
- A stalled TCP output does not stop RX receiving datagrams from its lanes; the output limit then declares the newest datagrams lost ([Thread-Per-Lane Blocking I/O](design.md#thread-per-lane-blocking-io)).

## Contracts

### Datagram Header

The header that every datagram carries ([Header Per UDP Datagram](design.md#header-per-udp-datagram)) has this layout ([Datagram Header Layout](design.md#datagram-header-layout)). It is always 24 bytes, followed by `payload_len` bytes of slice data. Multi-byte fields use network byte order (big-endian). The sequence wire field is u64 even in reduced-width rollover-test builds. Version remains 1 throughout pre-alpha wire changes; version bumps begin with formal releases. There is no per-datagram application checksum.

| Field         | Offset (bytes) | Size (bytes) | Byte order | Purpose                                                                                                               |
| ------------- | -------------- | ------------ | ---------- | --------------------------------------------------------------------------------------------------------------------- |
| magic         | 0..2           | 2            | network    | Constant `0x534D` ("SM"); marks a socket-mux datagram.                                                                |
| version       | 2              | 1            | n/a        | Header format version, 1.                                                                                             |
| flags         | 3              | 1            | n/a        | Bit 0 = end of stream; bits 1 to 7 are zero.                                                                          |
| payload_len   | 4..6           | 2            | network    | Number of slice-data bytes after the header.                                                                          |
| session       | 6..8           | 2            | network    | Random 16-bit ID for this TX run.                                                                                     |
| sequence      | 8..16          | 8            | network    | Global slice sequence number across all N lanes: 0 for the first slice, one more modulo 2^S for each following slice. |
| stream_offset | 16..24         | 8            | network    | Byte offset of this slice's first byte in the original stream, modulo 2^64; it rolls over like the sequence number.   |

The datagram size includes this header. At a 1500-byte adapter MTU the default datagram size is 1452 bytes, leaving 1452 - 24 = 1428 payload bytes, and at the default 64 MiB RX memory limit W = floor(67108864 / 1452) = 46218 datagrams.

## Semantics

- Session ([Session Identity And Restart](design.md#session-identity-and-restart)): TX (`tx` and `tx-pat`) chooses a random 16-bit session ID at start, logs `session=<n>` at `info`, and carries that ID in every datagram, including end of stream. RX locks onto the session of its first valid datagram. A valid datagram from a different session triggers a `warn` log and ends the current stream exactly as end of stream does: RX delivers what the ordering and loss rules allow in order, closes its TCP output, prints its final summary and exits 0. It does not deliver the different session's payload. A new stream requires a fresh RX process; there is no resume. A repeated session ID cannot distinguish runs, and the first valid datagram may belong to a stale session ([known limits](known-issues.md#register)).
- Ports ([RX Listen Ports](design.md#rx-listen-ports)): lane k, for k from 0 to N - 1, uses base port + k on both sides. TX sends lane k to `--remote` at base port + k; RX listens on the same ports. The operator supplies both sides the same lane count, base port and datagram size by hand; there is no negotiation.
- Loss: RX determines packet loss and the length of that loss from the datagram headers. The sequence gap gives the lost slice count and the stream-offset gap gives the lost byte length; RX skips the lost bytes, keeps the order of the bytes it delivers, and counts the loss stretch with its cause in its loss report (S-09). RX declares a missing sequence number lost only under timeout rule A or B or the memory limit below.
- Input: `tx` splinters its input across the N UDP lanes, and RX reassembles it on the remote end, so `tx` and RX act like a netcat split over N UDP lanes. `tx` accepts `-` (standard input) or a file as its input.
- Pattern: `tx-pat` generates a sequence of 4096-byte blocks, starting at block index 0. Each block contains an 8-byte big-endian index starting at zero, 4084 bytes of SplitMix64 payload keyed by the seed and index, and a 4-byte big-endian Adler-32 checksum of the first 4092 bytes. The SplitMix64 state starts at `seed XOR (index × 0x9E3779B97F4A7C15)` with wrapping 64-bit multiplication; each output step adds `0x9E3779B97F4A7C15`, applies the SplitMix64 mixing operations, and emits the result big-endian, truncating the last output to four bytes. Adler-32 starts with A = 1 and B = 0, uses modulus 65521, and stores `(B << 16) | A`.
- Pattern length (S-20): without `--bytes`, `tx-pat` runs until a send error or a signal and sends no end-of-stream datagram. With `--bytes N`, it sends exactly the first N bytes of the pattern, so the last block may be partial, then marks its final datagram with the end-of-stream flag, prints its final summary and exits 0.
- Pacing (S-21): with `--ipd-ns NS` above 0, `tx-pat` numbers its datagrams i = 0, 1, 2, ... across all lanes in sequence order and sends datagram i no earlier than start + i × NS, where start is the time it begins sending. A datagram already past its due time is sent without delay, so the long-run rate never exceeds one datagram per NS. With 0, `tx-pat` sends as fast as its lanes accept datagrams.
- End of stream ([Inter-Packet Delay Timeout](design.md#inter-packet-delay-timeout)): the end-of-stream datagram carries a sequence number and a payload of zero or more bytes. RX processes it only in sequence order, or when the timeout releases it under rule A or rule B below. Rule B therefore also ends a stream whose end-of-stream datagram was lost. `tx` marks its final datagram with the end-of-stream flag after its input ends, and RX closes its TCP output after delivering through that datagram.
- Timeout ([Inter-Packet Delay Timeout](design.md#inter-packet-delay-timeout)): RX has one timeout, T, and applies two rules with it. Each arrival below is an arrival time ([Terminology](#terminology)).
  - Rule A: a run of missing sequence numbers is declared lost once T has passed since the arrival of the datagram just before the run, which is the received datagram with the highest sequence number below the run. Every sequence number in the run expires with it, and RX delivers on in sequence order from the next datagram it holds.
  - Rule B: once T has passed since the last datagram RX received, with no new datagram, RX declares every remaining gap lost, delivers everything it holds in sequence order, and ends the stream.
  - Worked example: datagrams 1, 2, 6 and 7 arrive at 0 s, and the stream continues to 10005 and 10006 at 10 s. With T = 10 s, at 10 s the inter-packet delay from 2 to 3 has expired, so 3 is lost, and 4 and 5 expire with it as one loss stretch of 3 slices.
- Start of stream: RX waits without a limit for its first valid datagram, locks onto its session and anchors on it. Sequence ordering and timeout rules apply within that locked session. If that datagram's sequence number is s0, RX waits at most T from its arrival for sequence numbers older than s0: an older datagram that arrives within T is placed and delivered in sequence order. Once T has passed since that arrival, RX declares the older sequence numbers still missing lost and proceeds; it never waits longer, because a longer wait would break the timeout T. An older datagram that arrives later is late.
- Memory limit: RX memory holds both the datagrams waiting behind the gap at next and the datagrams awaiting their TCP write, and the memory limit declares a gap lost on either of two triggers, both with the `memory` cause.
  - Distance: a datagram whose sequence number is at least next + W has no place in RX's memory. RX declares the run at next lost, and the run after it as needed, until the datagram fits.
  - Memory reserve: the memory reserve R is W ÷ 4, rounded down and limited to the range 1 to 4096 datagrams; it is a threshold, not memory set aside. Once the start of stream has settled (RX no longer waits for sequence numbers older than its first datagram), after each arrival that is neither late nor a duplicate, while the free RX memory is at most R datagrams, the datagrams RX holds behind the gap at next number at least R, and they outnumber the datagrams awaiting their TCP write, RX declares the run at next lost and delivers on in sequence order from the next datagram it holds. Releasing the gap at this threshold is meant to leave free memory for arrivals while the TCP output writes the released datagrams; arrivals can still use that memory up first.
- Output limit: when no RX memory is free, RX drops the newest datagram and counts it as lost. Output-cause loss means that no RX memory was free for an arriving datagram. The memory reserve is meant to release a gap before the datagrams held behind it fill RX memory, so output-cause loss points first to datagrams awaiting their TCP write, a TCP output that has fallen behind the arriving stream; arrivals that use up the free memory before RX orders them, or a gap held during the start of stream, can also leave no memory free.
- Late and duplicate datagrams: a datagram whose sequence number RX has already delivered or declared lost, or whose sequence number RX already holds, is dropped and counted in the loss report.
- Loss limits: T, the RX memory limit and the TCP output are three independent limits on what RX holds. T is the slow limit: rules A and B bound how long a datagram waits behind a gap. The RX memory limit is the fast limit: it bounds how far ahead of a gap RX holds datagrams. A gap holds at most W - 1 datagrams behind it, and the memory reserve can release it sooner, so the depth a gap is guaranteed to hold is about W - R less the datagrams awaiting their TCP write: about 42,100 datagrams at the default W of 46,218 (R = 4096), and three quarters of W when W is below 16,384. The TCP output is the third limit: RX keeps each datagram's memory until its TCP write completes, so a slow TCP consumer fills the RX memory and the output limit drops. T covers slow arrival and the RX memory limit covers fast arrival, so each is set without changing the other.
- Backpressure: TX waits for each of its own UDP sends to complete, but RX sends no backpressure to TX. When the TCP consumer is slow, RX keeps receiving and retains datagrams until its memory is full, then the output limit drops newest datagrams as loss; there is no separate TCP-output-stall timeout.
- Sequence numbers: they always roll over, modulo 2^S, and RX compares them with serial-number arithmetic: s is after next when (s - next) mod 2^S is below 2^(S-1), and before next when it is above. RX tolerates no sequence ambiguity: a gap of half the sequence space, 2^(S-1), is a fatal error, and RX logs it and exits with status 1. W must therefore be below 2^(S-1). The stream offset rolls over the same way, modulo 2^64, and RX computes the stream-offset gap of a loss modulo 2^64.
- Loss report (S-09): from its first valid datagram until its stream ends, RX prints one interval report at the end of each reporting interval (S-26), counted from the arrival of that datagram, and, when it ends, one final summary; the final summary alone covers a last, incomplete interval. With `--interval 0` RX prints only the final summary. Lost-slice and lost-byte counts are exact. Each loss stretch is reported to the summary path through a bounded queue of 4096 entries; when that queue is full, the stretch's slices still count as lost, its report event is counted as dropped (`events_dropped`), and the stretch count and longest stretch cover the reported events only. With debug logging on, late and duplicate datagrams also send events through that queue and can count as dropped. A stretch still open at the end of an interval is counted in that interval, and its continuation is counted as a new stretch in the next.
- Report units: byte counts and rates count payload bytes only, in decimal units with three significant digits (1 GBytes is 10^9 bytes, 1 Gbit/s is 10^9 bits per second); a byte count below 1000 is printed exactly, as `512 Bytes`. The RX final summary spans from the arrival of the first valid datagram to the completion of the last TCP write; the TX final summary spans from TX framing its first datagram to the completion of its last send. Interval times count seconds from the same start.
- TX report (S-22): from framing their first datagram, `tx` and `tx-pat` print one interval report at the end of each reporting interval (S-26), and one final summary when they end: after end of stream, on a send error and on SIGINT or SIGTERM.
- Signals (S-23): on SIGINT or SIGTERM, `tx`, `tx-pat` and RX stop, print every loss and summary fact recorded so far in their final summary, and exit with status 130 for SIGINT and 143 for SIGTERM. On Windows, Ctrl-C has the SIGINT effect and status, and closing the console has the SIGTERM effect and status. After such a signal TX sends no end-of-stream datagram, and RX stops writing to its TCP output: datagrams it still holds or has not yet written are not delivered, and it closes that connection. A second SIGINT or SIGTERM ends the process at once with the status of the first. A process that has not ended 2 s after the first signal, for example `tx` waiting for terminal input on standard input, prints its final summary if it has not yet done so and exits with that status.
- Datagram size and MTU: without `--datagram-size`, each side's datagram size is its adapter MTU ([Terminology](#terminology)) less 48 bytes (the 40-byte IPv6 and 8-byte UDP headers), limited to the range 25 (the 24-byte header and one payload byte) to 65507, so one datagram fits one frame of that adapter; when the adapter MTU cannot be read, the default is 1452. `--datagram-size` overrides the default and accepts 25 to 65507 bytes. Each side logs its effective datagram size and its source once at start (S-25). When the datagram size exceeds the adapter MTU less 48, the side also logs one warning (S-24) and proceeds. A datagram larger than the path MTU less 48 bytes is fragmented by IP, and losing one fragment loses the whole datagram; a smaller MTU elsewhere on the path draws no warning ([known issues](known-issues.md#register)). The two sides derive their defaults from different adapters, and RX discards a datagram larger than its own datagram size, so where the two adapter MTUs differ the operator gives both sides the same `--datagram-size`.
- Verification loop: TX and RX can be placed back to back in a verification loop, with either `tx` or `tx-pat` as TX.

## Validation

- Pattern verification: `check-pat` reads RX's output from standard input. It finds valid 4096-byte windows by Adler-32 and, when `--seed` is given, also regenerates and compares the payload. It accepts a block whose index follows the prior accepted index; otherwise it searches forward one byte at a time for the next valid window and reports resynchronization. Without a seed, it checks the checksum and index order but cannot verify the pseudorandom body.
- Checker report: one line is printed in the form `check-pat: blocks_ok=<n> blocks_bad=<n> resyncs=<n> lost_bytes=<n> skipped_bytes=<n> trailing_bytes=<n> first_index=<index|none> last_index=<index|none>`. It reports valid and bad blocks, resynchronizations, inferred missing bytes, bytes skipped while searching, bytes after the last complete valid block, and first/last accepted indices; absent indices are `none`. A `tx-pat --bytes` run whose N is not a multiple of 4096 leaves a partial final block, which `check-pat` counts as trailing bytes.

## Diagnostics

TX and RX print diagnostics through their log on standard error, at the levels below; `--log-level`, `-v` and `-q` select which levels appear. Each diagnostic is one log line; the logger begins it with a bracketed UTC timestamp in milliseconds, the level and the module, for example `[2026-10-30T00:31:09.432Z INFO  socket_mux::rx]`, and the text below follows. In the formats below, `<span>` is `[<from>-<to> s]` with each time in seconds to two decimals, padded to five characters; `<bytes>` is a byte count such as `1.17 GBytes`; and `<rate>` is a rate such as `9.38 Gbit/s`.

- UDP buffer (S-19): once per side, `--udp-buffer` logs `udp buffer requested=<n> effective=<m>` at `info`. The effective size is the socket readback divided by two on Linux, unchanged elsewhere. If effective < requested, RX or TX warns that the OS capped it; on Linux the warning names sysctl `net.core.rmem_max` (RX) or `net.core.wmem_max` (TX). Without the option, the OS-default effective size is logged at `debug`. Capping is not an error.
- Datagram size above adapter MTU (S-24): trigger: TX or RX starts with a datagram size above its adapter MTU less 48 bytes; facts: the datagram size, the adapter MTU and that datagrams of this size fragment; at `warn`, once per side, then the side proceeds. No warning is logged when the adapter MTU cannot be read. The line reads `datagram size <size> exceeds <adapter> mtu <mtu> less 48; datagrams will be IP-fragmented and a lost fragment loses the datagram`.
- Datagram size (S-25): trigger: TX or RX starts; facts: the effective datagram size and its source, at `info`, once per side: `datagram size <size> (<adapter> mtu <mtu>)` for a size derived from the adapter MTU, with `; clamped` before the closing parenthesis when the 25 to 65507 limit changed it; `datagram size <size> (--datagram-size; <adapter> mtu <mtu>)` or `datagram size <size> (--datagram-size; mtu unknown)` for a given size; and `datagram size 1452 (default; mtu unknown)` when no size is given and the adapter MTU cannot be read.
- Session (S-17): trigger: `tx` or `tx-pat` starts, or RX locks onto the session of its first valid datagram; facts: `session=<n>`, the session ID; at `info`.
- New RX session (S-18): trigger: RX receives a valid datagram with a session ID different from its locked session; facts: `new session <n> (current <m>); ending stream`; at `warn`, then the current stream ends under the session rule and RX exits 0.
- RX interval report (S-09): trigger: the end of each reporting interval from RX's first valid datagram until its stream ends; facts: the interval's start and end time since the first datagram, the payload bytes RX delivered in the interval and their rate, the slices lost in the interval, the number of loss stretches, the lost slices per loss cause and the longest loss stretch in slices; at `info`, as `<span>  <bytes>  <rate>  lost <n> datagrams in <k> stretches (memory <m> output <o> timeout <t>) longest <l>`, for example `[ 3.00- 4.00 s]  1.17 GBytes  9.38 Gbit/s  lost 15 datagrams in 2 stretches (memory 0 output 15 timeout 0) longest 12`.
- RX final summary (S-09): trigger: RX ends after it connected its TCP output, by end of stream, timeout rule B, a different session, SIGINT or SIGTERM, or a runtime failure; facts: the run's span, payload bytes delivered and average rate, delivered bytes and datagrams, lost slices and lost bytes, the number of loss stretches, lost slices per loss cause, the longest loss stretch, late and duplicate datagrams dropped and, when nonzero, the dropped report events; at `info`, as `rx summary: <span>  <bytes>  <rate>  delivered <b> bytes in <d> datagrams  lost <x> datagrams <y> bytes in <k> stretches (memory <m> output <o> timeout <t>) longest <l>  late <a> duplicate <u>`, followed by `  events_dropped <e>` when e is above 0.
- RX end of stream: an end by timeout rule B logs `timeout <T> expired with no datagrams; ending the stream: total_lost_slices=<n> total_lost_bytes=<n>` at `info`, with T as, for example, `10s`; a different session logs the S-18 line and a signal the S-23 line; an end of stream by the end-of-stream datagram logs no separate line.
- Loss detail: at `debug`, RX also logs one `loss gap: cause=<cause> first_seq=<n> lost_slices=<n> lost_bytes=<n>` line per loss stretch and one `discarding late datagram: seq=<n>` or `discarding duplicate datagram: seq=<n>` line per late or duplicate datagram, subject to the same bounded queue as the loss report.
- TX interval report (S-22): trigger: the end of each reporting interval from TX framing its first datagram; facts: the interval's span, payload bytes sent and their rate, and datagrams sent; at `info`, as `<span>  <bytes>  <rate>  sent <n> datagrams`.
- TX final summary (S-22): trigger: `tx` or `tx-pat` ends after end of stream, on a send error or on SIGINT or SIGTERM; facts: the run's span, payload bytes sent and average payload rate, and payload bytes and datagrams sent; at `info`, as `tx summary: <span>  <bytes>  <rate>  sent <b> bytes in <d> datagrams`. A send error is logged at `error`; a signal logs the S-23 line.
- Signal (S-23): trigger: the first SIGINT or SIGTERM; facts: `received SIGINT; stopping` or `received SIGTERM; stopping` at `info`; when the process has not ended 2 s later, `did not stop within 2s; exiting` at `warn`.
- Sequence ambiguity: trigger: a gap of half the sequence space; facts: next and the received sequence number; at `error`, then exit status 1.
- Exit status: see [Exit Status](#exit-status).

## Boundaries

- Throughput and error rate: socket-mux makes no zero-loss guarantee at any rate; datagram loss is normal on its lossy channel. The success of a transfer, including a qualification run, is judged by its total error rate, not by the absence of loss. On a 10 Gbit/s link through a single switch the target delivered fraction is three to five nines, 99.9 % to 99.999 %, so a run on such a link that delivers less than 99.9 % misses the target. On a 10GbE path near line rate, the receiving host's network adapter can drop rare datagrams before RX sees them ([known issues](known-issues.md#register)).
- Platforms ([First-Release Platform Targets](design.md#first-release-platform-targets)): the first-release (MVP) qualification scope is Linux x86_64 with a static musl build. Qualification requires both a file transfer and a `tx-pat`/`check-pat` run to pass on a real target machine; a successful cross-build alone is not a pass. A qualification run passes when its delivered fraction meets the error-rate target; a file transfer is judged by that target, not by equal checksums of the sent and received files, because a lossy run's output differs from its input. Linux x86_64 is qualified on this baseline, on the code of commit `908a81d`: on two Linux x86_64 hosts over 10GbE, file transfers and pattern runs at one and four lanes in both directions each delivered at least 99.999 % of the datagrams sent, and 68 of the 72 runs of a link sweep delivered at least 99.995 %; the other 4 sweep runs fell in events of known issue `KI-13` ([known issues](known-issues.md#register)) and delivered 23 % to 99 % ([Measured Link Behavior](design.md#measured-link-behavior)). Linux aarch64 is built but not tested; qualification is deferred. Windows 10/11 x86_64 is built but not yet qualified; qualification is next, pending the Windows peer. macOS was tested on an earlier build without a recorded version or architecture; the current build has not been re-tested on macOS, and that re-test is deferred.
- Security ([Trusted-Link Security Boundary](design.md#trusted-link-security-boundary)): socket-mux is for trusted or private links only. Lane traffic is neither encrypted nor authenticated: anyone on the path can read it, and anyone who can reach RX's UDP ports can inject datagrams. To cross an untrusted network, run socket-mux inside a VPN, for example WireGuard. Session IDs are not authentication.
- Retransmission is out of scope at this stage.
