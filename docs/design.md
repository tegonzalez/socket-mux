# socket-mux Design

## Purpose

Describe the architecture and mechanisms of socket-mux for authors implementing, extending or reconsidering it. The design covers one Rust binary carrying one input stream or generated pattern over N UDP lanes and reconstituting it, plus an independent pattern-checking subcommand.

## Orientation

The intended baseline is a Rust 2021 binary whose TX and RX run on blocking operating-system threads without an async runtime ([Thread-Per-Lane Blocking I/O](#thread-per-lane-blocking-io)); `check-pat` reads standard input and opens no socket. Realization evidence is uneven: the per-lane TX send threads exist in the source tree, while the RX threads, the loss and summary reporter and signal handling are intended structure whose realization is not yet evidenced, because their implementation is being replaced. The inventory distinguishes intended responsibility from realized modules, with source paths as implementation evidence. Forbidden implementation patterns are in the [constraints](constraints.md).

## Terminology

| Term                                     | Design use                                                                                                                |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| TX, RX                                   | Transmit and receive roles; consumer-visible meanings are owned by the [specification](spec.md#terminology).              |
| Lane, slice, sequence, session           | Units used to split, address and order the stream; exact meanings are owned by the [specification](spec.md#terminology).  |
| Datagram header                          | The TX-to-RX contract carried on every UDP datagram; the [specification](spec.md#datagram-header) owns its exact layout.  |
| Timeout T, RX memory limit, output limit | Independent RX waiting and capacity bounds; exact behavior is owned by the [specification](spec.md#semantics).            |
| Loss stretch, loss cause                 | A run of slices RX declares lost together, and why; exact meanings are owned by the [specification](spec.md#terminology). |
| Producer                                 | The TX thread that reads or generates the input and frames datagrams for the lane send threads.                           |
| Reorder thread                           | The one RX thread that owns the wheel and every ordering, timeout, loss-cause and session decision.                       |
| Free list                                | The lock-free list of unused pool buffers that threads take from and return to.                                           |
| Loss ring                                | The bounded lock-free queue of loss-stretch events from the reorder thread to the reporter; a push never waits.           |
| Reporter                                 | The low-priority thread that prints interval reports and final summaries.                                                 |

## Design Goals

- Carry one input stream over configurable UDP lanes and reconstitute it at RX (G1); one program supports both sides (G2).
- Order received slices and determine loss and its byte length without retransmission (G3, G4).
- Support a back-to-back verification loop with a generated pattern that remains locatable after loss (G6).
- Preserve cross-platform operation (G7). Configurable lane-count behavior (G5) remains a consumer requirement owned by the [specification](spec.md#public-surface).
- Let throughput scale with lanes toward line rate, keeping per-datagram work constant and off shared locks (G1).
- Use approximately no CPU while idle, and keep loss reporting from ever slowing the data path (G1, G3).

## Architecture

- **Program.** One program has TX and RX network modes and the `tx`, `tx-pat`, `rx` and `check-pat` subcommands ([One Program With TX And RX Subcommands](#one-program-with-tx-and-rx-subcommands)). `check-pat` reads standard input and opens no socket. The [specification](spec.md#command-line) owns options, defaults, precedence and exit statuses.
- **TX path.** TX reads one input and splinters its byte stream efficiently into N UDP lanes, each on a different port, selected from a base port incremented by one by default ([TX Splinters Over N Ports](#tx-splinters-over-n-ports)). Sequence s is assigned to lane s mod N ([Round-Robin Slice Assignment](#round-robin-slice-assignment)). Every datagram carries a header ([Header Per UDP Datagram](#header-per-udp-datagram)), whose layout the [specification](spec.md#datagram-header) owns. A producer thread reads or generates the input and frames datagrams into pool buffers; it hands each lane's datagrams through a bounded queue to that lane's send thread, which sends them with blocking calls on a UDP socket connected to `--remote` at base port + k ([Thread-Per-Lane Blocking I/O](#thread-per-lane-blocking-io)).
- **TX input.** The `tx` subcommand reads one TCP connection on localhost, standard input (`-`) or a file, like netcat ([One Program With TX And RX Subcommands](#one-program-with-tx-and-rx-subcommands)); the [specification](spec.md#command-line) owns how the operator selects among them. The `tx-pat` subcommand generates a pseudorandom pattern from a random seed or `--seed` ([Self-Locating Adler Pattern Blocks](#self-locating-adler-pattern-blocks)); it is unpaced and endless by default, and `--ipd-ns` paces it and `--bytes` ends it with an end-of-stream datagram ([TX-PAT Byte Count And Pacing](#tx-pat-byte-count-and-pacing)).
- **RX path.** RX listens on base port to base port + N - 1, the same ports TX sends to ([RX Listen Ports](#rx-listen-ports)). The operator supplies both sides the same lane count, base port and datagram size; there is no negotiation. One blocking receive thread per lane receives each datagram directly into a buffer from the preallocated RX pool and passes it, with its arrival time, through a bounded lock-free queue to the one reorder thread. The reorder thread reads each header, applies the session rule, sequences slices, determines packet loss and its length and cause, and passes ordered buffers through a bounded queue to the TCP writer thread, which writes the reconstituted stream and returns each buffer to the pool ([RX Reconstitutes The Stream](#rx-reconstitutes-the-stream), [Thread-Per-Lane Blocking I/O](#thread-per-lane-blocking-io)). The [specification](spec.md#public-surface) owns where RX delivers that stream and what it reports where it detects loss.
- **Loss.** Neither mode retransmits, so the channel is lossy ([No Retransmission](#no-retransmission)).
- **Seam.** The UDP datagram, a header followed by slice data and at most the [datagram size](spec.md#terminology), is the one seam between TX and RX, seam `SM-01`. The [specification](spec.md#datagram-header) owns the header layout.
- **Verification loop.** TX and RX can be placed back to back in a verification loop ([Back-To-Back Verification Loop](#back-to-back-verification-loop)). With `tx-pat` as TX, `check-pat` validates RX output against the pattern, with byte-wise resynchronization after loss ([Self-Locating Adler Pattern Blocks](#self-locating-adler-pattern-blocks), [Check-Pat Checker Subcommand](#check-pat-checker-subcommand)).
- **Delivery order and timeout.** RX delivers strictly in sequence order. It settles every gap and the end of the stream with one timeout T, under the rules the [specification](spec.md#semantics) states, and times them from arrival times ([Inter-Packet Delay Timeout](#inter-packet-delay-timeout)).
- **RX ordering.** The reorder thread orders datagrams in a wheel indexed by sequence number within a fixed RX memory limit, then hands them in order to the TCP writer ([RX Memory Limit, Wheel And FIFO](#rx-memory-limit-wheel-and-fifo)). It alone makes ordering, timeout, loss-cause and session decisions.
- **Allocation.** Neither mode allocates heap memory per datagram; both draw buffers from preallocated pools through lock-free free lists ([No Heap Allocation In The Critical Path](#no-heap-allocation-in-the-critical-path)).
- **I/O and waiting.** TX and RX use blocking operating-system threads and no async runtime ([Rust Crate Set](#rust-crate-set), [Thread-Per-Lane Blocking I/O](#thread-per-lane-blocking-io)). Socket waits are blocking calls; a thread waiting on a queue spins briefly, then backs off to a blocking park ([Wait Policy](#wait-policy)).
- **Reporting.** The reorder thread keeps exact loss counters and pushes one compact event per loss stretch into a bounded lock-free ring that never blocks; a low-priority reporter thread prints RX interval reports and the TX and RX final summaries ([Loss And Summary Reporter](#loss-and-summary-reporter)).
- **Signals.** SIGINT and SIGTERM, and the Windows Ctrl-C and console-close events, make the reporter drain and print the final summary before the process exits with 130 or 143 ([Signal Handling And Final Summary](#signal-handling-and-final-summary)).
- **Session.** TX assigns a random run identity in its header path; RX checks it before sequence placement and uses its existing end-of-stream path when the identity changes ([Session Identity And Restart](#session-identity-and-restart)). This is intended architecture; it does not assert verified realization.
- **Security.** The lane path has no encryption or authentication layer; an external VPN protects an untrusted link ([Trusted-Link Security Boundary](#trusted-link-security-boundary)).
- **Platforms.** One code base targets Linux, macOS and Windows, and every dependency is cross-platform ([Cross-Platform Dependencies](#cross-platform-dependencies)); first-release qualification is [First-Release Platform Targets](#first-release-platform-targets).

### Deployment And Test Topology

The available test topology is two identical Linux x86_64 hosts, each with an AMD Ryzen AI Max+ PRO 495 and 32 threads, connected over 10GbE at a 1500-byte MTU and addressed over IPv4. The receiving host's 10GbE adapter runs one receive queue with a 256-entry receive ring. An administrator raised `net.core.rmem_max` and `net.core.wmem_max` to 67108864 bytes (64 MiB) on the Linux hosts with `sysctl -w`, which lasts until reboot; the Linux default for each is 4194304 bytes. Socket-buffer capacity is separate from the RX memory limit that bounds application-held datagrams. The repository's `scripts/link-sweep` harness drives two-host runs over lanes, RX `--udp-buffer`, `--ipd-ns` and `--datagram-size`, and records UDP, adapter and softnet counters on each host's local disk.

The intended deployment adds a headless Windows x86_64 peer as TX, receiving the cross-compiled `win64-x86_64` binary without a build environment on the peer. The performance goal is maximum throughput from Windows TX to Linux RX. The [roadmap](roadmap.md#r-39-per-layer-measurement-plan) owns measurement readiness and sequencing, including jumbo-MTU work, which waits for the Windows peer.

### Measured Link Behavior

These two-host Linux 10GbE measurements used 1452-byte datagrams and `tx-pat --bytes` runs; they ground the decisions below. The payload ceiling at 1452-byte datagrams is about 9.41 Gbit/s over IPv4 and 9.29 Gbit/s over IPv6 (arithmetic: 10 × 1428 / 1518 and 10 × 1428 / 1538 wire bytes per datagram).

| ---------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |

| One blocking send thread reaches about 5.8 Gbit/s; two or more lanes, each with its own send thread, reach about 9.4 Gbit/s.       | [Thread-Per-Lane Blocking I/O](#thread-per-lane-blocking-io)                                                                |

## Design Decisions

### Rust Crate Set

| Field             | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Decision          | socket-mux is implemented in Rust on the standard library's blocking threads, synchronization and networking, with no async runtime. The crate set is `socket2` for socket options, `windows-sys` for Windows Winsock and console events, `lexopt`, `anyhow`, `log` and `env_logger`, plus small single-purpose crates for lock-free bounded queues (for example `crossbeam-queue`) and cross-platform signal handling (for example `ctrlc`). Tokio is not a dependency. |
| Rationale         | A fixed set of N long-lived lane sockets maps directly onto one blocking thread each, which the standard library and `socket2` provide on Linux, macOS and Windows ([Thread-Per-Lane Blocking I/O](#thread-per-lane-blocking-io)). Blocking calls sleep in the kernel without CPU, so an async scheduler adds a hop and a shared core without adding capacity. Small queue and signal crates avoid hand-written lock-free and platform signal code.                      |
| Alternatives      | Tokio's current-thread runtime for TX and RX I/O; Tokio for the control plane only, beside per-lane threads; `pico-args` instead of `lexopt`.                                                                                                                                                                                                                                                                                                                            |
| Rejection reason  | On the current-thread runtime TX sent about 5.2 Gbit/s at every lane count and TX and RX each saturated one core ([Measured Link Behavior](#measured-link-behavior)). A control-plane-only runtime keeps a second concurrency model and dependency for work that blocking threads and the signal crate already cover. `lexopt` is the selected parser.                                                                                                                   |
| Affected surfaces | TX and RX I/O; signal handling; CLI; platform dependencies                                                                                                                                                                                                                                                                                                                                                                                                               |

### Inter-Packet Delay Timeout

### Thread-Per-Lane Blocking I/O

| Field             | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Decision          | TX: one producer thread reads or generates the input, assigns sequence numbers and frames each datagram into a pool buffer; it hands lane k's datagrams through a bounded queue to lane k's send thread, which sends them with blocking calls on a UDP socket connected to `--remote` at base port + k and returns each buffer to the pool. RX: one blocking receive thread per lane takes a buffer from the RX pool's lock-free free list, receives one datagram directly into it, records its arrival time and pushes it through a bounded lock-free queue to the one reorder thread. The reorder thread owns the wheel, the session rule, timeout rules A and B, the memory and output limits and every loss-cause decision ([RX Memory Limit, Wheel And FIFO](#rx-memory-limit-wheel-and-fifo)); it pushes in-order buffers through a bounded queue to one TCP writer thread, which writes them and returns each buffer to the free list. When the free list is empty, a receive thread receives into its own spare buffer and passes only that datagram's header facts to the reorder thread as an output-limit drop. Every thread waits under the [Wait Policy](#wait-policy). Pinning threads to cores is not part of this decision; it is [roadmap R-43](roadmap.md#r-43-per-lane-thread-pinning). |
| Rationale         | One send thread reaches about 5.8 Gbit/s and two or more lanes with their own send threads about 9.4 Gbit/s, near the 10GbE payload ceiling ([Measured Link Behavior](#measured-link-behavior)). Per-lane receive threads move the per-datagram receive cost off the ordering thread in the same way. One reorder thread keeps every ordering and loss decision in one owner, so the wheel needs no lock. A separate TCP writer means a stalled output cannot stop receiving; the RX memory limit and the output limit, not a blocked receive loop, then absorb the stall. Bounded queues and a fixed pool keep memory bounded.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Alternatives      | One async runtime thread for all sockets; receive threads that place datagrams in the wheel under a lock; one RX thread that receives, orders and writes; unbounded channels between threads.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Rejection reason  | One runtime thread caps throughput at one core ([Rust Crate Set](#rust-crate-set)). A shared wheel lock puts contention on every datagram and splits loss decisions across threads. A thread that also writes TCP output stops receiving whenever the output stalls, so socket buffers overflow instead of the specified output limit applying. Unbounded channels let memory grow past the RX memory limit.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Affected surfaces | TX path; RX path; S-04, S-07, S-15; [Wait Policy](#wait-policy); [Loss And Summary Reporter](#loss-and-summary-reporter)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

### Wait Policy

| Field             | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Decision          | Socket waits are blocking send and receive calls; no thread polls a socket or sets it nonblocking to spin on it. A thread waiting on a queue or the free list spins for a bounded time on the order of nanoseconds to microseconds, then yields, then sleeps for exponentially increasing times up to a cap, then parks until the producing thread unparks it. A thread that has a deadline, the reorder thread's rule A or rule B expiry, parks only until that deadline. The `--ipd-ns` pacer sleeps until shortly before a datagram is due and spins only the final stretch, which is bounded by the pacing schedule. The reporter sleeps until its next interval. |
| Rationale         | A short spin catches the next datagram within nanoseconds at line rate without a kernel wake per datagram, about 0.8 million datagrams per second at 9.4 Gbit/s of 1452-byte datagrams (arithmetic). Backoff to a blocking park lets an idle TX or RX, and an RX holding datagrams behind a gap, use approximately 0 % CPU.                                                                                                                                                                                                                                                                                                                                           |
| Alternatives      | Busy-polling sockets or queues; sleeping and polling on a fixed interval; blocking on a condition variable for every handoff.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Rejection reason  | Busy polling holds a core at 100 % while idle. Interval polling adds latency and still wakes the CPU. A blocking wake for every datagram puts a kernel call on each of about 0.8 million handoffs per second (derivation; unmeasured). The [constraints](constraints.md) forbid the first two.                                                                                                                                                                                                                                                                                                                                                                        |
| Affected surfaces | Every TX and RX thread; S-21 pacing; reporter; idle CPU                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

### RX Memory Limit, Wheel And FIFO

| Field             | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Decision          | RX holds datagrams in a preallocated pool of equal buffers whose total size is the RX memory limit (`--rx-memory`), each buffer one datagram of the datagram size; there are no variable-sized buffers. The [Hold capacity W](spec.md#terminology) is the RX memory limit ÷ datagram size, rounded down. Free buffers sit on a lock-free free list that the lane receive threads take from and the TCP writer returns to. The wheel is a ring of W slots indexed by sequence number mod W; each slot is tagged with the exact sequence number it holds and records its arrival time, and an occupancy bitmap marks the full slots. All W buffers can hold datagrams. The slot array, the bitmap, the queues and one spare datagram-size receive buffer per lane are fixed overhead outside the RX memory limit. The reorder thread places each received buffer's reference in the wheel slot of its sequence number. The wheel starts at the first datagram RX receives: older datagrams that arrive within T of it are placed normally, and once T has passed RX declares the older sequence numbers still missing lost ([specification](spec.md#semantics), start of stream). The reorder thread serves the wheel in sequence order: each present slot at next moves, by reference, to the ordered, gap-free FIFO queue that feeds the TCP writer thread, and its buffer returns to the free list when its TCP write completes. Only the reorder thread touches the wheel, so the wheel needs no lock. Per-datagram work is constant time: placement and release index the wheel directly, and finding the next held slot after a loss stretch walks forward from next once per stretch; nothing scans the wheel, W or the queued output per datagram ([constraints](constraints.md)). The reorder thread waits for its input queue until the earlier of rule A's and rule B's expiry ([Wait Policy](#wait-policy)). The [specification](spec.md#semantics) owns the RX memory limit, output, late and duplicate rules this structure applies. |
| Rationale         | The wheel places and finds each datagram by its sequence number in O(1). Equal buffers from one pool keep RX's receive memory bounded by the configured limit. One owner needs no locks, and one deadline lets the reorder thread sleep without polling. Per-datagram scans proportional to W or the output backlog made RX slowest exactly when it was behind and collapsed multi-lane goodput ([Measured Link Behavior](#measured-link-behavior)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Alternatives      | A heap ordered by sequence number; a duplicate check that searches the queued TCP output per datagram.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Rejection reason  | A heap takes every datagram after a second open gap and costs O(log H) per insert, where H is the number of datagrams held. A per-datagram search of the queued output grows with the backlog ([constraints](constraints.md)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Affected surfaces | RX reordering and loss declaration; RX output; S-09, S-14, S-15                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

### Output Under Loss

| Field             | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Decision          | Where RX detects loss, it skips the lost bytes, keeps the order of the bytes it delivers, and counts the loss stretch with its lost slice count (from sequence), byte length (from stream offset) and cause in the loss report ([Loss And Summary Reporter](#loss-and-summary-reporter)). ### Self-Locating Adler Pattern Blocks

| Field             | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

### Loss And Summary Reporter

| Field             | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Decision          | The reorder thread keeps exact counters of delivered datagrams, lost slices and lost bytes per loss cause, and late and duplicate drops, published without locks; the TCP writer keeps the delivered-byte counter. For each loss stretch it pushes one fixed-size event, carrying cause, first sequence number, slice count and byte length, into a bounded lock-free ring. A push never waits: when the ring is full the event is discarded and an overflow counter is incremented. One low-priority reporter thread wakes once per reporting interval, drains the ring, reads the counters and prints one RX interval report; when the stream ends or a signal arrives it drains the ring again and prints the RX final summary. TX keeps sent-byte and datagram counters, and its reporter prints the TX final summary. Report lines summarise stretches and counts; nothing prints per datagram or per stretch. The [specification](spec.md#diagnostics) owns the reported facts. |
| Rationale         | Loss reporting must never interfere with the critical path or maximum throughput. Formatting and writing a log line per loss stretch on the ordering path flooded the log under heavy loss and slowed RX into more loss ([Measured Link Behavior](#measured-link-behavior)). Exact counters keep totals correct even when the ring overflows; the ring keeps per-stretch detail, the stretch count and longest stretch, off the hot path. Interval lines in the manner of iperf3 show rate and loss as a run progresses.                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Alternatives      | One log line per loss stretch; per-stretch lines rate-limited to a fixed number per second with the rest summed; a blocking channel from the reorder thread to the reporter.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Rejection reason  | Per-stretch lines are unbounded hot-path logging ([constraints](constraints.md)). Rate limiting still formats and writes lines on the reorder thread and reports stretches rather than the interval's rate and totals. A blocking channel lets a slow reporter stall ordering.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Affected surfaces | S-09, S-22; reorder thread; reporter                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

### Signal Handling And Final Summary

| Field             | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Decision          | `tx`, `tx-pat` and RX install a handler for SIGINT and SIGTERM, and on Windows for the Ctrl-C and console-close events, through the cross-platform signal crate ([Rust Crate Set](#rust-crate-set)). The handler only records which signal arrived and wakes the reporter. The reporter drains the loss ring, prints the final summary with the signal as the end reason, and the process exits with 130 for SIGINT or Ctrl-C and 143 for SIGTERM or console close, without waiting for threads blocked in socket calls. |
| Rationale         | Measurement runs and long transfers end by a signal; the final summary must survive that end, and 130 and 143 follow the shell convention of 128 plus the signal number. Recording the signal and waking the reporter keeps the handler trivial and leaves the data-path threads untouched.                                                                                                                                                                                                                              |
| Alternatives      | The operating-system default disposition, with no handler.                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Rejection reason  | The default disposition ends the process before any summary, so the run's loss and rate are lost.                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Affected surfaces | S-23; M-01; reporter                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

### TX-PAT Byte Count And Pacing

| Field             | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

| Decision          | `tx-pat --bytes N` limits the generated pattern to its first N bytes; the producer frames the last slice with the end-of-stream flag, and `tx-pat` exits 0 after it is sent. `tx-pat --ipd-ns NS` gives datagram i, counted across all lanes, the due time start + i × NS; the producer releases each datagram to its lane no earlier than its due time, sleeping for long waits and spinning only the final stretch, and releases a late datagram at once. 0 leaves `tx-pat` unpaced.                                                                               |

A due-time schedule keeps the average rate exact without accumulating sleep error, and spinning only the final stretch keeps spacing at microsecond scale within the [Wait Policy](#wait-policy). Pacing did not remove the rare receive-ring loss on the measured link ([Measured Link Behavior](#measured-link-behavior)), so the default stays unpaced. |
| Alternatives      |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

### UDP Socket Buffer Sizing

| Field             | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Decision          | `--udp-buffer` requests each UDP send buffer on TX and each UDP receive buffer on RX; without it both sides keep the operating-system default. TX and RX read the effective size back and report a capped request ([specification](spec.md#diagnostics)). Operators size the RX receive buffer and leave the TX send buffer at the default; a larger RX default is [roadmap R-37](roadmap.md#r-37-proposal-larger-default-rx-udp-buffer).                                       |
| Rationale         | An RX receive buffer of 16 MiB or more removes UDP receive-buffer errors at about 9.4 Gbit/s, while 4 MiB does not; a large TX send buffer lets the sending host queue more than the link carries and drop datagrams in its queueing discipline ([Measured Link Behavior](#measured-link-behavior)). Linux caps each request at `net.core.rmem_max` or `net.core.wmem_max`, which only an administrator raises, so the readback makes a cap visible instead of silent. |
| Alternatives      | One large default buffer on both sides.                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Rejection reason  | A large TX buffer causes sender-side drops ([constraints](constraints.md)).                                                                                                                                                                                                                                                                                                                                                                                            |

## Component Responsibilities

| Role                         | Responsibility                                                                                                               |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| TX producer (`tx`, `tx-pat`) | Read or generate one stream, apply `--bytes` and `--ipd-ns`, sequence slices and frame each datagram for its lane.           |
| TX lane send thread          | Send its lane's datagrams with blocking calls on its connected socket and return their buffers.                              |
| RX lane receive thread       | Receive its lane's datagrams into pool buffers with blocking calls and pass them, with arrival times, to the reorder thread. |
| RX reorder thread            | Apply the session rule, order slices, apply timeout rules and loss limits, count loss and release in-order buffers.          |
| RX TCP writer thread         | Write the reconstituted stream and return written buffers to the free list.                                                  |
| Reporter                     | Print RX interval reports and TX and RX final summaries, including after a signal.                                           |
| Checker (`check-pat`)        | Independently scan RX output and report pattern validity and resynchronization.                                              |

## API Shape

The package exposes a command-line binary, not a Rust library API ([`Cargo.toml`](../Cargo.toml), [`src/main.rs`](../src/main.rs)). The [specification](spec.md#public-surface) owns the CLI and the UDP datagram shape. `SM-01` is the only cross-role data seam; this design describes its architectural use and does not duplicate its field schema.

## Workflow And Data Flow

The operator configures both endpoints with the same lane count, base port and datagram size by hand; there is no negotiation. TX sends lane k to `--remote` at base port + k, while RX listens on those same ports. Sequence s is assigned to lane s mod N. The TX producer frames datagrams and hands them through bounded queues to the lane send threads; each send thread waits for completion of its own blocking UDP sends, and a full lane queue makes the producer wait, so TX runs at the rate its lanes accept. RX sends no backpressure to TX. The RX lane receive threads hand datagrams to the reorder thread, which applies the single timeout T and RX memory limit and hands ordered buffers to the TCP writer. A slow TCP consumer holds buffers in the writer queue until the memory limit is reached; the receive threads keep receiving, and the output limit drops new datagrams as loss. Loss-stretch events and counters flow to the reporter without blocking. `tx-pat` supplies blocks until `--bytes` ends it with an end-of-stream datagram, or without end when no byte count is set; the independent checker reads the resulting RX output from standard input.

```text
TX:  input or pattern -> producer -> lane queue k -> send thread k -> UDP base port + k   (k = 0 .. N-1)
RX:  UDP base port + k -> receive thread k -> reorder thread -> writer queue -> TCP writer -> original stream
     pool free list <- TCP writer;  receive thread k <- pool free list
     reorder thread -> loss ring and counters -> reporter -> interval and final lines
     RX output -> check-pat
```

## Failure Modes

- **Datagram loss.** RX determines packet loss and the length of that loss from the headers; nothing is retransmitted ([No Retransmission](#no-retransmission)). The [specification](spec.md#semantics) owns what RX reports where it detects loss. RX declares loss only under the [specification's](spec.md#semantics) timeout rules and loss limits ([Inter-Packet Delay Timeout](#inter-packet-delay-timeout), [RX Memory Limit, Wheel And FIFO](#rx-memory-limit-wheel-and-fifo)).
- **Deep reorder or fast burst.** A datagram W or more ahead of next triggers the memory limit before T ([RX Memory Limit, Wheel And FIFO](#rx-memory-limit-wheel-and-fifo)).
- **Stalled TCP output.** TX waits only for completion of its own UDP sends; RX applies no backpressure to TX. The RX receive threads keep receiving while buffers wait for their TCP writes until RX memory is full, then the output limit drops new datagrams ([Thread-Per-Lane Blocking I/O](#thread-per-lane-blocking-io), [RX Memory Limit, Wheel And FIFO](#rx-memory-limit-wheel-and-fifo)).
- **Heavy loss.** Loss-stretch events beyond the loss ring's capacity are discarded and counted; loss totals stay exact and the data path is not slowed ([Loss And Summary Reporter](#loss-and-summary-reporter)).
- **Small socket receive buffer.** An RX receive buffer below about 16 MiB overflows at about 9.4 Gbit/s on 10GbE, which the host counts as UDP receive-buffer errors and RX reports as loss; on Linux an administrator must raise `net.core.rmem_max` before a larger `--udp-buffer` takes effect ([UDP Socket Buffer Sizing](#udp-socket-buffer-sizing)).
- **Large TX socket buffer.** The sending host queues more than the link carries and its queueing discipline drops datagrams ([UDP Socket Buffer Sizing](#udp-socket-buffer-sizing)).
- **Adapter receive-ring overflow.** Near line rate the RX host's adapter, with one receive queue and a 256-entry ring on the measured host, misses rare datagrams before any socket, and pacing does not remove this; RX reports them as ordinary loss ([known issues](known-issues.md#register), [roadmap R-34](roadmap.md#r-34-linux-gro-receive-and-lane-steering)).
- **Datagram above the path MTU.** A `--datagram-size` above the path MTU less 48 bytes is IP-fragmented; losing any fragment loses the datagram, so loss rises sharply ([known issues](known-issues.md#register)).
- **TX restart or stale session.** A different session invokes stream finalization, not a sequence reset or resume ([Session Identity And Restart](#session-identity-and-restart)); same-ID collisions and stale-first arrivals remain [accepted limits](known-issues.md#register).
- **Dead lane.** RX reports every gap a later datagram exposes. If the dead lane carried the end-of-stream datagram, timeout rule B ends the stream T after the last datagram ([Inter-Packet Delay Timeout](#inter-packet-delay-timeout)).
- **Signal.** SIGINT or SIGTERM ends TX or RX with its final summary and status 130 or 143 ([Signal Handling And Final Summary](#signal-handling-and-final-summary)).

## Acceptance Criteria

- **AC-01:** TX assigns sequence s to lane s mod N and sends lane k to the same base-port-plus-k endpoint on which RX listens, as required by the [specification](spec.md#semantics).
- **AC-02:** RX delivers in order and applies the specified timeout, RX memory limit and output limit without retransmission or feedback to TX ([specification](spec.md#semantics)).
- **AC-03:** `tx-pat` output can be sent through RX and independently checked by `check-pat`, including recovery after loss ([Back-To-Back Verification Loop](#back-to-back-verification-loop), [specification validation](spec.md#validation)).
- **AC-04:** Settings remain command-line-only and both endpoints rely on operator agreement rather than negotiation ([Command-Line Options](#command-line-options), [specification](spec.md#semantics)).
- **AC-05:** TX and RX run without an async runtime: one send thread per TX lane, one receive thread per RX lane, one reorder thread and one TCP writer thread, and RX keeps receiving while its TCP output is stalled ([Thread-Per-Lane Blocking I/O](#thread-per-lane-blocking-io)).
- **AC-06:** An idle TX or RX, and an RX holding datagrams behind a gap, uses approximately 0 % CPU, and no socket is polled ([Wait Policy](#wait-policy), [specification invariants](spec.md#invariants)).
- **AC-07:** Under induced heavy loss, RX prints only interval and final-summary lines, its lost-slice totals are exact, and loss-ring overflow is counted rather than waited on ([Loss And Summary Reporter](#loss-and-summary-reporter)).
- **AC-08:** SIGINT and SIGTERM end `tx`, `tx-pat` and RX with their final summary and status 130 or 143 ([Signal Handling And Final Summary](#signal-handling-and-final-summary), [specification exit status](spec.md#exit-status)).
