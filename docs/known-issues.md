# socket-mux Known Issues

## Purpose

Register the admitted, finite residuals in socket-mux TX and RX behavior that each name one owning durable specification and would change a product or verification outcome once that owner absorbs them.

## Orientation

The audience is a reviewer or implementer of socket-mux who needs to know which current residuals to watch, an operator who meets one in a run, and an author of the owning document who decides what it must say next. This register records what each residual is and which document owns it. It states no required behavior, sequences no work and declares no readiness; a missing rule is added to the owner named in the entry. Prospects are in the [roadmap](roadmap.md).

## Terminology

| Term            | Meaning                                                                                                                                                                                                                                 |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reorder buffer  | The datagrams RX holds out of order in its wheel ([design](design.md#rx-memory-limit-wheel-and-fifo)) until it delivers them or declares a gap lost.                                                                                    |
| Loss acceptance | The rule by which RX stops waiting for a missing slice and declares it lost: timeout rule A or B, or the RX memory or output limit.                                                                                                     |
| Receive ring    | The network adapter's ring of receive descriptors; when it is full, the adapter drops arriving frames before any socket sees them and counts them as missed.                                                                            |
| Path MTU        | The largest IP packet every hop between TX and RX carries without fragmentation.                                                                                                                                                        |
| `rx_missed`     | The adapter's count of frames it missed because its receive ring was full, read from `/sys/class/net/<interface>/statistics/rx_missed_errors`; on the measured RX host's adapter (driver r8169) it is 16 bits wide and wraps at 65,536. |
| Miss burst      | A run in which the RX host's adapter misses more than 10,000 datagrams at once, as opposed to the few scattered misses per run of `KI-10`.                                                                                              |

### KI-13 Adapter Miss Bursts At Stream Start

- Symptom: RX's final summary reports a large loss, 16,908 to 1,630,967 datagrams in the measured runs; in the link sweep, which recorded the causes and host counters, all of it was `memory` cause, with no `output` loss and no UDP receive-buffer errors. Where RX printed interval lines, the whole loss fell in the first 2 s of the stream, in the interval starting at 0 s or at 1 s, and the rest of the run was clean. The run delivers 22 % to 99.2 % of its datagrams, so it misses the specification's 99.9 % error-rate target ([throughput boundary](spec.md#boundaries)); a transfer or qualification run with a miss burst fails that target.
- Recognition: the loss equals the increase of the RX adapter's `rx_missed` counter taken modulo 65,536, plus a whole multiple of 65,536 (0 to 24 times in the measured runs), plus a remainder of at most 153 datagrams. Because the counter wraps at 65,536, a raw before-and-after difference can be negative or far smaller than the loss; [`scripts/link-sweep/sweep-rx.sh`](../scripts/link-sweep/sweep-rx.sh) reports the difference modulo 65,536. The RX host's kernel log shows no adapter reset and the link does not flap (its `carrier_changes` count is unchanged).
- Occurrence: 10 of 162 socket-mux 3 GB pattern runs from one Linux host to the other over 10GbE in 1452-byte datagrams burst: 2 of 30 two-lane runs with RX `--udp-buffer` 64 MiB, 3 of 30 such runs with RX and its TCP sink pinned to CPUs 1 to 31, away from the adapter's interrupt CPU 0, 1 of 30 two-lane runs at 4 MiB, and 4 of the 72 link-sweep runs, with 2, 4 and 8 lanes at 16 and 64 MiB, unpaced and paced to 8.47, 7.62 and 5.71 Gbit/s ([measurements](design.md#measured-link-behavior)).
- Comparison: none of 90 iperf3 UDP runs of 3 GiB in 1428-byte payloads over the same link burst, with 2 or 4 streams, default socket buffers, and with or without a 9.4 Gbit/s loopback TCP stream on the RX host. iperf3 reached only 8.58 to 8.59 Gbit/s against socket-mux's about 9.4 Gbit/s, so the comparison is not rate-matched; the paced socket-mux bursts make rate alone an unlikely cause.
- Workaround: none known; rerun the transfer. In the measured runs with interval lines each burst stayed within the first 2 s and the rest of the run was clean, and 152 of the 162 measured runs had no burst; nothing measured guarantees that a rerun avoids one. Larger RX socket buffers, pacing and CPU pinning do not prevent it.
- Owner and next action: the [specification](spec.md#boundaries) owns the error-rate target this residual misses. The next diagnostic needs administrator (root) access on the RX host: trace the receive path during stream start with `perf` or `ftrace`, and sample `ethtool -S` every second through the first seconds of the stream, to tell whether socket-mux's start-of-stream behavior or its higher packet rate, about 820,000 against iperf3's 752,000 datagrams per second (payload rate over 1428 × 8 bits per datagram), triggers the bursts.

## Boundaries

This register holds only admitted residuals in accepted TX and RX behavior. Desired evolution is in the [roadmap](roadmap.md), current behavior in the [specification](spec.md), and mechanism in the [design](design.md). Implementation holes, task lists and test cases are not admitted here.
